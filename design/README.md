# design/

@kazuemon/ui のデザイン原則を、候補の生成と選定を繰り返してブラッシュアップするための作業場所です。

## ディレクトリ構成

| パス               | 中身                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `principles.md`    | 原則と判断の基準（なぜそうするか）                                                                                                            |
| `tokens.css`       | 現行版の値。Tailwind v4 の `@theme` にそのまま取り込める形式                                                                                  |
| `adr/`             | 決定の記録。1決定につき1本（書き方は [`adr/README.md`](./adr/README.md)）                                                                     |
| `adr/assets/`      | ADR に添える比較画像。1本につき1枚                                                                                                            |
| `references/`      | 原則の出どころになった参照画像（一覧は [`principles.md`](./principles.md#参照画像)）                                                          |
| `rounds/rNN/`      | 各ラウンドの候補定義（`candidates.mjs`）と、ラウンド開始時点の現行版（`base-tokens.css`）。生成物は `build/` に出力され、git では管理しません |
| `rounds/p1-final/` | 前半の最終版。候補を持たず、前半の決定をすべて反映した現行版だけを描きます                                                                    |
| `tools/`           | 候補の生成ツール、比較画像の撮影ツール、色の計算                                                                                              |

値は `tokens.css` の1か所だけに書きます。`principles.md` と ADR は、値ではなく役割トークン名（`--color-primary` など）で参照します。

## ループの全体像

ブラッシュアップは2段階で進めます。

|                   | 前半                                                        | 後半                                                   |
| ----------------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| 目的              | ムードを決める                                              | 状態と動きを1軸ずつ詰める                              |
| 扱う軸            | トークン層と動き                                            | 画像と原則の食い違い、原則どうしの矛盾、残りの未決事項 |
| 1ラウンドで振る軸 | 未決の軸をすべて同時に                                      | 1軸だけ                                                |
| 提示方法          | design キャンバス                                           | Storybook                                              |
| 終了条件          | 子の4案が現行版に勝てないラウンドが2回続く（上限6ラウンド） | 軸のリストが空になる                                   |

前半の上限に達した場合は、残った軸を後半に回します。各軸の一覧は [`principles.md` の「軸の一覧」](./principles.md#軸の一覧) にあります。

  - 軸 13「キーボード操作時のフォーカス」は、2回の比較で B（ボタン・リンク・トグルは、キーボードで操作したときだけ 2px の青い線を 2px 離して描く。動くのは線の色だけ）に決まりました（[ADR-0031](./adr/0031-focus-visible.md)）。入力欄は原則2の枠線のままです。フォーカスの線は `src/components/focus-styles.ts` にまとめ、ボタン・リンク・トグルで共有します。文字のリンクの角丸（`--link-text-radius`）を 0px から 6px に変え、[ADR-0030](./adr/0030-text-link.md) に追記しました。軸 12 の比較のストーリーは、角丸を 0px に固定しました。Select のボタンで、青い枠線にブラウザの既定の線が重なって出ていた不具合も直しました
  - 軸 14「和文の縦位置の補正」は、A（和文フォントの縦の寸法を、漢字の枠に合わせる）に決まりました（[ADR-0032](./adr/0032-text-offset.md)）。ユーザーは C（和文と英大文字の中間）も考えていましたが、困っていたこと（入力欄の和文が上に寄る、入力欄と Select で縦位置がずれる）だけを直す A になりました。IBM Plex Sans JP の `@font-face` に `ascent-override: 88%`・`descent-override: 12%`・`line-gap-override: 0%` を足し、英字フォント（Mulish）は元のままです。`@fontsource/ibm-plex-sans-jp` の CSS は書き換えられないため、`scripts/generate-fonts.mjs`（`pnpm run fonts`）で補正を足した `src/styles/ibm-plex-sans-jp.css` を作り、`src/styles/globals.css` から読むようにしました。`@fontsource/ibm-plex-sans-jp` を更新したら、流し直します。補正したあとは、入力欄でも div でも、和文の差が 0.00px になりました（[`principles.md` の「和文の縦位置」](./principles.md#和文の縦位置)）。軸 14 の比較のストーリーは、現行版の行を元の寸法で上書きして再現しています。入力欄に和文の値を入れているほかの比較のストーリーでは、値が約 1px 下がります。これまでの ADR の比較画像は、撮った時点の見た目のままです
  - 軸 15「塗りのボタンを押したときの縁」は、2回の比較で A（押しても輪郭の 1px の線を残し、消すのは落ち影だけ）に決まりました（[ADR-0033](./adr/0033-press-edge.md)）。軸 14 を比べている途中で、ユーザーが「グレーの方は小さくなる挙動も入っているように見えます」と気づいたことから始めた軸です。押すと影の中の輪郭の線まで消えるため、白地に近いグレーのボタン（`#EFF0F1`）は縁が1周内側に下がり、縮んだように見えていました。「一旦 A で進めます。」とのことなので、使ってみて違和感があれば見直します。押したときの影を `--shadow-raised-press`（hover と同じ輪郭の線）にし、ボタン（`src/components/Button.tsx`）はここから読むようにしました。グレーのボタンの影と枠線もトークンにしましたが、比べた案を比較のストーリーで再現するためのもので、値はほかの塗りのボタンと同じ影、枠線なしです。原則3の【固定】「影を完全に消すのは押下に取っておく」は書き直し、hover と押下は 1px 沈むことで見分けるようにしました。[ADR-0006](./adr/0006-button-shadow.md) には、押下の影を変えたことを追記しました
  - 軸 16「ボタンの送信中（loading）」は、5回の比較で、E を既定にし、B と C も選べる形に決まりました（[ADR-0034](./adr/0034-loading.md)）。送信中は押せないボタンと同じ見た目にし、印（回る円・線）だけは薄くしません。E はラベルを 55% に薄くして回る円を重ねる形、B はラベルの左に回る円、C は下端に流れる線です。回る円は元の文字の色、線はボタンの濃い色です。押せない見た目への切り替わりは F1（押下と同じ緩急で 0.2 秒。出るときも戻るときも）です。ボタン（`src/components/Button.tsx`）に `loading` と `loadingIndicator`（`overlay`・`inline`・`bar`）を足しました。送信中は `aria-disabled`・`aria-busy` を付け、`disabled` 属性は付けないので、フォーカスは外れません。押しても何もせず、フォームも送信しません。印を薄くしないため、ボタン全体の `opacity` は使わず、塗り・文字・枠線の色を Disabled の薄さで混ぜています。そのため、`disabled` を切り替えたときの色の変化も 0.2 秒で動くようになりました。比較のストーリーに、実装した Button を確かめる「実装した Button」を足しました。入力欄と Select の送信中、動きを減らす設定のときの回る円と線は、まだ決めていません。薄くなった色のボタンの上では、白い回る円が弱く見えます（白との比は約 1.7）
  - 軸 17「入力欄の prefix・suffix」は、3回の比較で、A（文字もボタンも入力欄の端に接した塊）を既定にし、B（内側に 4px 浮かせる形）も選べる形に決まりました。エラーのときは、塊の塗りを赤み（`#F1E0DE`）にし、文字の色は変えません（[ADR-0035](./adr/0035-field-addon.md)）。部品（`src/components/FieldAddon.tsx`）を先に作り、形と色をトークンで切り替えて比べました。TextField に `prefix`・`suffix`・`addonShape` を、Select に `prefix`・`addonShape` を足しました。端に接する形では、塊が本体の枠線の色を受け継ぐので、フォーカスとエラーの枠線が塊の外側にも続きます。suffix に入れるボタンは、パスワードの表示・非表示のように入力欄そのものを操作するものに限り、検索のように内容を送るボタンは欄の外に置くことにしました。[ADR-0024](./adr/0024-neutral-button.md) には、決定2の「検索ボタンなど」を見直したことを追記しました。目のアイコン（`EyeIcon`・`EyeSlashIcon`）も、この軸のために足しました。入力欄が出てくる ADR の比較画像を撮り直し、この軸の変更で見た目が変わっていないことを確かめました。suffix のボタンにキーボードでフォーカスしたときの見せ方と、文字の prefix の読み上げは、まだ決めていません
  - 軸 18「Select の選択肢」は、2回の比較で E1（白い面に 1px の細い境界線とやわらかい影。選んだ項目は淡い青）に決まりました（[ADR-0036](./adr/0036-select-popup.md)）。1回目は、影で浮かせる A、輪郭をはっきりさせる B、選んだ項目を淡い青にする C、欄と同じグレーの面 D を比べました。2回目は、A の影と C の青に、A と B の間の濃さの輪郭を合わせた E1〜E3 を比べました。輪郭は白いボタンの輪郭と同じ `#DEE0E1`、選んだ項目は青のタグと同じ組み合わせです。浮かぶ UI の影は、押せることではなく重なりを表すものとして、原則1に例外として足しました（「原則1もかなり最初の方に決めたので、例外があってもいいなあとは思います。」）。浮かぶ部分の見た目をトークン（`--select-popup-*`・`--color-select-*`）にし、Select（`src/components/Select.tsx`）はここから描くようにしました。Select に `open`・`defaultOpen`・`onOpenChange`・`modal`・`container`・`collisionAvoidance` を足しました。比較のストーリーで、開いたままの選択肢を行ごとに並べるために使っています。Select が出てくる ADR の比較画像を撮り直し、閉じた Select の見た目が変わっていないことを確かめました。開いた直後は、選んだ項目がキーボードで選んでいるのと同じ状態になり、一段濃い青で表示されます。開くときと閉じるときの動きは仮のままです。影のトークンは Select の選択肢だけのもので、ほかの浮かぶ UI で同じ影を使うかは、それぞれを作るときに決めます
  - 軸 19「Select のボトムシート」は、シートを6回、浮かぶ選択肢を3回比べ、指で操作していて画面が狭いときは選択肢を画面の下から出すシートにすることに決まりました。長い選択肢は、シートでも浮かぶ選択肢でも途中で切り、上下の端の印で続きを見せます（[ADR-0037](./adr/0037-select-sheet.md)）。シートは、出し方、長い選択肢の見せ方、続きの印の順に比べ、O（上の端は区切り線をいつも出し、上下の端に内側の影）に決まりました。右上に固定した ×、後ろを暗くする背景、ラベルとヘルプテキストを1つにまとめた見出しを付けます。長いときは画面の高さの約半分で開き、つまみで高さいっぱい（85%）まで広げます。浮かぶ選択肢は、S（画面の高さの半分。ただし 10.5 項目まで。上下の端に内側の影）に決まりました。項目の数の上限は「一旦」です。切り替えの基準は、最初は原則11のとおり画面の幅（640px 未満）としていましたが、ユーザーのメモ「シートを使う利点は、ユーザーの指の動きを緩和するためだと思っています。そうなると、幅が基準にはならないかもしれません。」を受けて、指で操作していて（`pointer: coarse`）、縦長なら 768px（`md`）未満、横長なら 1024px（`lg`）未満のときにしました。タブレットとマウスは浮かぶ選択肢のままです。原則11の「構造は画面幅」を Select について見直し、[ADR-0004](./adr/0004-density-and-structure-switching.md) に追記しました。Select（`src/components/Select.tsx`）に `presentation`（`auto`・`popover`・`sheet`。既定は `auto`）を足しました。あわせて足した `sheetDetent`・`sheetMoreCue`・`popoverMoreCue`・`popoverMaxHeight` は、既定が決まった形で、ほかの値は比べた案を比較のストーリーで再現するために残しています。シートは Base UI の Select の浮かぶ部分を画面の下に固定して作り、つまみを引く操作は自前です。× とつまみで閉じるため、開閉を部品の中でも持つようにしました。閉じる × のアイコン（`XIcon`）も足しました。トークンは `--select-sheet-radius`・`--color-select-sheet-backdrop`・`--color-select-sheet-edge-shadow`・`--shadow-select-sheet`・`--duration-sheet`・`--ease-sheet`・`--select-popup-max-rows` です。1回目で、開くと後ろの画面が上にずれることが分かりました（「ボトムシートが出てくるときにレイアウトシフトが起きて、フォーカスが解除されたり後ろのコンテンツが上にずれたりしますね。」）。比較用のスマートフォンの枠が `overflow: hidden` で、スクロールできる箱になっていたためです。開いた直後にフォーカスが枠の外にある選択肢へ移り、枠の中身がずれていました。枠を `overflow: clip` に直し、実際の画面の幅（375px）でもずれないことを確かめました。選んだあとに本体の青い枠線が一瞬消える不具合も直しました（「あと、選択肢を選んだ後に一瞬青の枠線が消えるのが気になっています。」）。Base UI が閉じる動きのあとでフォーカスを本体に戻すためで、フォーカスが戻るまで、開いているときの見た目を保ちます。外を押して閉じたときは保ちません。浮かぶ選択肢の上下の余白を選択肢の内側に移し、面を角丸で切り抜くようにしたので、[ADR-0036](./adr/0036-select-popup.md) の比較画像を撮り直すと、面の角の 18 ピクセルだけが最大 5/255 違います。見ても分からない差なので、画像はそのままにし、ADR-0036 に追記しました。軸 18 の比較のストーリーの開いたままの列は、比べたときの見た目（上限と影なし）で固定しました。入力欄と Select が出てくるほかの ADR の比較画像は、撮り直しても変わっていません。つまみを引く速さ（勢い）は見ないこと、開いたまま画面の大きさを変えても高さを計算し直さないこと、Provider で固定する仕組みがまだないこと、項目の数の上限が「一旦」であることは、まだ決めていません
  - ADR の比較画像は、[`tools/capture-story.mjs`](#storybook-のストーリーを撮る後半) でストーリーを撮ります
  - ADR-0019〜0024 の比較画像は、[ADR-0032](./adr/0032-text-offset.md)（和文の縦位置の補正）より前に撮ったものです。そのため、今の見た目とは少し違います。撮り直すかは決めていません
  - **次にやること**: 残りの軸は [`principles.md` の「後半の軸」](./principles.md#後半の軸storybook-で1軸ずつ詰める) にあります。軸 19 までが終わりました。次の軸は、ユーザーが選びます。候補は、Warning、指用の高さ 44px（実機）、リンクの大きさ、入力欄・Select の送信中と動きを減らす設定、prefix・suffix の残り、Select の残りです。指用の高さ 44px は、軸 19 の「実機で確かめる」ストーリーでシートを指で確かめるときに、あわせて押してみられます

## 前半の1ラウンド

### 候補の構成

1ラウンドで **4候補＋現行版** を並べます。探索範囲が狭くなったら、候補数を減らしてかまいません（ラウンド4は3案＋現行版）。1候補は次の2つで構成します。

- **見本シート**: Button、TextField、Select、Switch、Tag、Card を、指用とマウス用の2つの密度で左右に並べたもの。2密度の差は仮の値（44px／36px）で固定し、前半では振りません
- **画面1枚**: Biography 風のモバイル画面。編集できる欄と読み取り専用の欄を混在させ、原則7・8・9をまとめて確かめます

画面のレイアウト層の装飾（背景の大きな文字など）は全候補で共通にし、比較の変数にしません。

各候補の artboard には、その候補の**トークン表と規則表**を併記します。選んだ時点で、何を保存するかが確定するようにするためです。

### 候補の作り方（進化的な絞り込み）

1. 初回は、名前の付く方向を4案作り、広く散らします
2. 2回目以降は、現行版を親にして、**まだ決まっていない軸だけ**を変えた子を4案作ります
3. 変える幅は、ラウンドを追うごとに狭めます

決まった軸は親から引き継がれ、固定されます。

### 一貫性の担保

- **候補の中**: 1候補を1つのトークン表と1つの規則表から生成します。規則を破る候補や、コントラスト基準（[ADR-0002](./adr/0002-contrast-and-foreground-tokens.md)）を満たさない候補は出しません
- **ラウンド間**: 毎回、現行版を候補と並べて置きます。新しい候補を選んだ結果、前の決定と矛盾する場合は、その場で指摘します

### 選び方

ユーザーは、[判断の基準](./principles.md#判断の基準)に最も近い候補を1つ選び、一言メモを添えます（例: 「B。角丸が好き」）。一貫性は生成の仕組みで担保しているので、判断するのは基準への近さだけです。

複数の候補から部分ごとに選んでもかまいません（例: 「影は A、角丸は C」）。その場合は、部分ごとに ADR を書きます。

キャンバス上で候補に手を加えた場合は、その差分も「保存すべき特徴」として記録します。

全候補がどれも違うと感じた場合は、全却下にします。その場合も「この方向は違うと分かった」ことを反例として記録します。

## 後半の1ラウンド

- 1軸につき1本のストーリーを `design/stories/axis-NN-*.stories.tsx` に置きます。Storybook では `Design Review/NN 軸の名前` に並びます
- 現行版と候補を行に、状態（通常・フォーカス中など）を列に並べます。枠は `design/stories/Comparison.tsx` です
- 候補は、`design/tokens.css` への上書き（CSS 変数）だけで作ります。部品のコードは候補ごとに分けません。前半と同じく、候補の中の一貫性を仕組みで担保するためです。今のトークンで表せない案が必要になったら、先に部品をトークンで表せる形に直します
- 候補は、全案（現行版を含む）で軸の値を明示します。決まって `tokens.css` を更新した後も、同じ比較を再現するためです。前半の `base-tokens.css` の代わりです
- 決まったら、ストーリーの `pick` の既定値を採用した案にし、説明の先頭に決定と ADR の番号を書きます。ストーリーは記録として残します
- hover やフォーカスのように、操作しないと出ない状態は、`storybook-addon-pseudo-states` で固定して並べます。「通常」の列の部品は実際に操作できるので、動きも確かめられます
- 指用とマウス用の密度は、ツールバーの「密度」で固定して比べます（[ADR-0004](./adr/0004-density-and-structure-switching.md)）
- 密度の差は実機で指で押して詰めます
- 選び方は前半と同じです。ユーザーはストーリーを開き、1案を選んで一言添えます

## ツールの使い方

### ラウンドを始める

1. `design/tokens.css` を `design/rounds/rNN/base-tokens.css` にコピーして固定します。ラウンドの記録（候補の見た目や比較画像）を、後から同じ条件で再現するためです。以降、`tokens.css` を更新しても、そのラウンドの候補は `base-tokens.css` を土台に描かれます
2. `design/rounds/rNN/candidates.mjs` に候補を書きます。各候補は `base-tokens.css` への上書きとして定義します
3. 生成します

   ```sh
   node design/tools/generate-round.mjs design/rounds/rNN
   ```

   `design/rounds/rNN/build/` に、キャンバス用の artboard（`*.dc.html`）、`canvas.json`、ローカル確認用の `preview.html` が出力されます。コントラスト基準を満たさない候補があると、どの組み合わせが何対何で足りないかを表示して中止します

`candidates.mjs` の `candidates` を空にすると、現行版だけを描きます。前半の最終版（`rounds/p1-final/`）はこの形です。キャンバスの説明の付箋は、`spec.brief` で差し替えられます。

### 比較画像を撮る

ADR に添える比較画像は、次のコマンドで撮ります。現行版と全候補の同じ部品を横に並べ、`--pick` で指定した案に「採用」の印を付けます。

```sh
node design/tools/compare.mjs design/rounds/rNN \
  --parts <buttons|fields|switches|tags|card をカンマ区切り> \
  --pick <採用した案の ID> \
  --title "ADR-NNNN タイトル" \
  --out design/adr/assets/NNNN-kebab-title.png
```

- `--height` で画像の高さを調整します（既定は 640px）。部品が多いときは大きくします
- `--note` で副題を足せます
- 撮ったら、下端が切れていないかを目視で確認します

候補は `base-tokens.css` を土台に描かれるので、`tokens.css` を更新した後でも、そのラウンドの見た目で撮れます。

ラウンドの候補とは別の比較を ADR に添えたいときは、`--spec` で候補定義のファイルを差し替えます（既定は `<round>/candidates.mjs`）。例えば [ADR-0011](./adr/0011-switch-off-track.md) の画像は、スイッチ OFF の輪郭の有無だけを並べる定義 `design/rounds/r02/adr-0011-switch.mjs` で撮りました。

```sh
node design/tools/compare.mjs design/rounds/r02 \
  --spec design/rounds/r02/adr-0011-switch.mjs \
  --parts switches --pick 現行版 \
  --title "ADR-0011 スイッチ OFF のトラック" \
  --out design/adr/assets/0011-switch-off-track.png
```

### Storybook のストーリーを撮る（後半）

後半の ADR に添える比較画像は、比較のストーリーをそのまま撮ります。

```sh
node design/tools/capture-story.mjs design-review-01-focus--candidates \
  --pick A \
  --out design/adr/assets/NNNN-kebab-title.png
```

- Storybook をビルドし、ローカルで配信してストーリーだけを撮ります。ビルド済みのディレクトリがあれば、`--static-dir` で渡すとビルドを省きます
- `--pick` で、採用した案に「採用」の印を付けます（現行版は `current`）
- `--density coarse|fine` で密度を固定します。`--width`・`--height` で画像の大きさを調整します（既定は 1320×1500px）
- 動きを止めて撮ります（`prefers-reduced-motion`）。移り変わりの途中で撮られ、状態の見た目が出ないことがあるためです
- マウスで操作している環境（`hover: hover`、`pointer: fine`）として撮ります。撮影に使う headless Chrome は既定で「マウスなし」になり、hover の見た目が出ないためです。`--density coarse` のときは、指で操作している環境（`hover: none`、`pointer: coarse`）として撮ります
- 撮ったら、下端が切れていないかを目視で確認します

### 和文の縦位置を測る

入力欄の中で、文字のインクが上下どちらに寄っているかを画素で測ります（[`principles.md` の「和文の縦位置」](./principles.md#和文の縦位置)）。フォントの縦位置を補正したら、このコマンドで確かめます。

```sh
node design/tools/measure-text-offset.mjs
```

## ラウンド後に更新するもの

次の順で更新します。

1. **ADR を書く**: 決まったこと1つにつき1本。前の決定を覆した場合は、古い ADR を Superseded にします。全却下のラウンドも1本残します
2. **`tokens.css` を更新する**: 採用した候補の値を現行版に反映します
3. **`principles.md` の印を更新する**: 決まった軸は【前半の軸】【後半の軸】から【決定】に変え、根拠の ADR へリンクします。反例が増えた場合は「反例」の節に足します
4. **比較画像を撮る**: `tools/compare.mjs` で撮り、`adr/assets/NNNN-*.png` に保存します
