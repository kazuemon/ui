# レビューの点検表

AI が部品の PR をレビューするときに使う点検表です。人がレビューするときの手引きにもなります。原則（[`principles.md`](./principles.md)）が「どう見えるか」を書くのに対して、この表は「部品がどう書かれているべきか」を書きます。

## 使い方

- 指摘には、根拠として原則の番号か ADR の番号を必ず付けます。CLAUDE.md の「部品を作る」に根拠があるときは、その項目の番号を付けます
- 根拠を引けない指摘は、却下ではなく「原則にない判断」の候補として、まとめて別に出します。原則の空白を見つけるのがレビューの仕事の半分です
- 指摘は 3 つに分けます
  - **直す**: 原則・ADR・この表に反している。直し方も書く
  - **聞く**: 原則に沿っているが、読み方が 2 つあって決めきれない。両方の読み方を書く
  - **空白**: 原則も ADR も触れていない判断。PR の「原則にない判断」の一覧に入っているかを確かめる
- 好みや一般論（「普通はこうする」）では指摘しません。このライブラリの決まりだけを見ます
- トークンの値そのもの（px や色）は見ません。値は tokens.css にあり、原則はその根拠を書く場所です（ADR-0047）。見るのは、役割のトークンを使っているか、使っていない理由があるかです

## 2. props と API の決まり

- 色の props は `color` です。`tone`・`variant` などの別名を作りません。利用者が選ぶ色は `primary`・`secondary`、状態の色は `info`・`success`・`warning`・`danger` です（ADR-0051）
- 待っているあいだは `loading`（真偽値）で表し、印の形は `loadingIndicator`（`spinner`・`bar`）、欄を止めるかは `loadingBehavior`（`blocking`・`non-blocking`）です（ADR-0034、0042、0051）
- 配置を選ぶ props は `<何>Placement` の形で、値は `start`・`end` です（ADR-0049）
- 浮かぶ UI の構造は `presentation` で固定できます（ADR-0037）
- 既定値は部品の引数の既定値で持ち、JSDoc の `@default` と Storybook の `argTypes` の `table.defaultValue` に同じ値を書きます
- props の説明は JSDoc に書きます。何のための props か、どの原則に沿うかを 1〜2 文で書き、値は書きません
- 素の要素の props（`className`・`aria-*`・`data-*`）を通します。`className` は `tv` の `className` に渡し、`twMerge` で足せるようにします
- 部品が組み立てる文（エラーの文、読み上げの文）を持ちません。渡された文をそのまま出します（原則 20）
- 公開するものを `src/index.ts` に足しています。部品と props の型の両方です。内部の部品（`src/internal/`）は公開しません

## 3. 構造の決まり

CLAUDE.md の「部品を作る」に沿っているかを確かめます。

- 置き場所: `src/components/<kebab-name>/` に部品・ストーリー・基準画像。その部品だけが使う部分は同じフォルダ、2 つ以上の部品が使う部分は `src/internal/`
- 振る舞い（キーボード・読み上げ・開閉）は、Base UI にある部品を土台にしています。自前で作り直していません
- 見た目は `tv`（`src/internal/tv`）で書き、Tailwind のクラスで役割のトークンを使っています
- 生の値（px・色コード）をクラスや style に書いていません。役割にない値だけを部品のトークン（`--<name>-*`）として `design/tokens.css` の `:root` に足し、尺度（`--spacing`・`--radius-*`・`--border-width-*`・`--duration-*`）を指しています（ADR-0076）
- `@theme` に名前を足したら `twMergeConfig` にも足しています（ADR-0077。`tv.test.ts` が確かめます）
- 寸法は密度のトークン（`--spacing-control` など）で書き、`data-density` で切り替わります
- フォーカスの線は `focusRing`、ラベル・キャプション・エラーの行は `internal/field` の `Field`、Form の送信中は `useFormSubmittingLock`・`useChoiceLock` を使っています。同じ働きを部品の中で作り直していません
- 1 ファイルが大きくなったら、見た目の一部は `<Name>Part.tsx`、状態を持つ処理は `use-*.ts`、DOM を読むだけの計算は `*.ts` に分けています
- 新しい部品のクラスが Storybook に出るよう、`src/styles/globals.css` を touch しています（コミットには出ません。dev server での確かめのときだけ）

## 4. キーボードと読み上げ

- キーボードだけで、すべての操作ができます。Tab で止まる順が見た目の順です
- フォーカスの線は、キーボードで操作したときだけ出ます（`focus-visible`。ADR-0031）
- 押せないものは Tab で止まらず、読み上げでは「利用不可」と読まれます（ADR-0026、0073）。押せない理由をキャプションで伝えるときは、読めるままです
- ラベル・ヘルプテキスト・エラーが、読み上げで 1 回ずつ、見た目の順で読まれます。文字の prefix・suffix は説明の先頭に来て、見えている文字は読み上げから外します（ADR-0040、0044）
- エラーと警告は割り込まず（polite）、危険のお知らせだけが割り込みます（assertive）（ADR-0043、0044）
- 開閉するものは、開いたときにフォーカスが中へ移り、閉じたときに元へ戻ります。閉じたあとにフォーカスが body に落ちません（ADR-0075 の backlog を参照）
- 新しいタブで開くリンクは、読み上げに「新しいタブで開きます」を足します（ADR-0046）
- 動きを減らす設定で、大きな動きが止まるか明滅に置き換わっています（ADR-0042）

## 5. ストーリーとテスト

- タイトルは `Components/<Name>` です
- Docs の文は使い方だけです。開発の経緯・ADR の番号・比較の話を書いていません
- Controls で既定の値から始まります（`args` が部品の既定と同じ）
- 状態・色・密度の一覧に `tags: ['visual']` が付いています。操作しないと出ない状態（hover・押下・フォーカス）は `statePseudo` で固定しています。`Playground` と動きの途中は撮っていません
- `play` で、読み上げの名前と説明、props の働き、キーボード操作を確かめています。`userEvent` は `storybook/test` から読んでいます
- 基準画像（`__screenshots__/`）が PR に入っています。画像を見て、意図した見た目かを確かめます。既存の部品の画像が変わっていたら、変える理由が PR に書かれています
- `pnpm typecheck`・`pnpm lint`・`pnpm format:check`・`pnpm test` が通っています

## 6. 記録

- PR の本文に「原則にない判断」の一覧があります。判断ごとに、何を決めたか、どの原則に近いか、代わりの案を 1 行ずつ書いています
- 一覧の判断は、部品の中に「一旦」や「TODO」として残していません。決めた形で書き、迷いは一覧に出します
- README の部品の一覧にチェックが付いています
- backlog に足すべき未決事項（作らなかった状態、比べていない候補）が、PR の本文か backlog に書かれています

## 指摘の書き方

インラインのコメントは、1 件につき次の形です。

```
【直す】原則 2（ADR-0071）: フォーカスの線が青で固定されています。部品の色に従い、指定なしでは濃紺にします。`focusRing` を使うと、色は自動で従います。
```

```
【聞く】原則 5: 浮かぶ面の角を部品の角にしていますが、この部品はシートの仲間にも見えます。どちらの読み方かを決めてください。
```

まとめのコメントは、次の順です。

1. 直す・聞くの件数
2. 原則を引けなかった指摘（原則にない判断の候補）。PR の一覧にすでにあるものは除く
3. CI の結果（typecheck・lint・format・test のどれが落ちたか）
