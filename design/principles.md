# デザイン原則

このドキュメントは、コンポーネントを生成・実装する際の判断基準です。
個別の実装で迷ったときは、トークンの値ではなく**ここに書かれた「なぜ」に立ち返って**判断してください。

値は [`tokens.css`](./tokens.css) に、決定の経緯は [`adr/`](./adr/) にあります。ブラッシュアップの進め方は [`README.md`](./README.md) を参照してください。

前半（ムード探索）は終わりました。前半の決定をすべて反映した見た目は、[`rounds/p1-final/`](./rounds/p1-final/)（design キャンバスの最終版）で確認できます。

## 各項目の印

原則はまだブラッシュアップの途中です。各項目に次の印を付けています。

| 印           | 意味                                             |
| ------------ | ------------------------------------------------ |
| 【固定】     | 参照画像と原則が一致しており、ループでは振らない |
| 【決定】     | ループで決まった。根拠の ADR を併記する          |
| 【前半の軸】 | 前半（design キャンバス）でムードとして振る      |
| 【後半の軸】 | 後半（Storybook）で1軸ずつ詰める                 |

画像と原則が食い違っている箇所は、どちらも仮説として扱い、ループで決めます（[ADR-0001](./adr/0001-judgement-criteria.md)）。【固定】の項目でも、ループ中にユーザーが違和感を示した場合は軸に戻します。

# 存在理由

**デスクトップでもモバイルでも、それぞれに適した密度にすること。**

デスクトップ優先の UI はモバイルに合わず、モバイル優先の UI はデスクトップで密度が低くなります。このアンバランスを解消することが、このシステムを作る動機です（[原則11](#11-密度は入力方式構造は画面幅で切り替える)）。

# 判断の基準

候補を選ぶとき、また実装で迷ったときは、次の4語に最も近いものを選びます（[ADR-0001](./adr/0001-judgement-criteria.md)）。

| 基準の言葉     | 画面上で見るところ                                   |
| -------------- | ---------------------------------------------------- |
| **軽い**       | 影は弱く、線は細く、余白は多い                       |
| **やわらかい** | 角が丸い。文字は黒ではなく濃紺グレー（`--color-fg`） |
| **整然**       | 部品の構造が揃っている（3層構成、状態の規則）        |
| **人懐っこい** | 水色・ピンク・pill・和欧併記                         |

## 顔: 構造は実直、個性はトークン層

- **構造**（状態の表し方、影、塗りと枠線）は実直にします。参照画像のうち、コンポーネント見本の側に寄せます
- **個性**（色、角丸、文字、和欧併記）はトークン層に出します。参照画像のうち、Web サイトの側に寄せます

「整然」は構造が、「人懐っこい」はトークンが担います。

## ポップさの出し方: トークン層＋動き

温かみとポップさは、トークン層と動きで出します。動きは[原則3](#3-hover-は一段沈む)「一段沈む」の延長として、押下時にバネのように沈む、といった形にします。

コンポーネントの内部に装飾を持ち込むことはしません（[原則9](#9-遊びはレイアウト層に置く)）。

## 反例

次のような見た目は、基準から外れています。ループで却下した候補から、ここに追加していきます。

- マテリアルデザインのような、影で階層を作る硬い見た目
- 字間を大きく空けた英字ラベル。AI が作ったように見えます（[ADR-0010](./adr/0010-section-label.md)）

# 原則

## 1. 影は「押せること」の記号

影は**塗りのあるボタンにのみ**付けます。それ以外（カード、フォーム部品、枠線のみのボタン）には付けません。【固定】

この規則により、3つの状態が区別できます。押せるかどうかは影の有無で、押せないこと（Disabled）は本体の薄さや色でも示します（[ADR-0026](./adr/0026-disabled.md)）。

| 見た目                                                                                                      | 意味                 |
| ----------------------------------------------------------------------------------------------------------- | -------------------- |
| 塗りがある + 影がある                                                                                       | 押せる               |
| 枠線のみ + 影なし                                                                                           | 押せるが主役ではない |
| 影がない + 本体が薄い（色を持つ部品）、または明るいグレーと薄い文字の色の組み合わせ（入力欄・グレーの部品） | 押せない（Disabled） |

白いボタン（面の塗り）も「塗りがある + 影がある」押せるボタンとして扱います。ただし、白い地の上では影だけでは区別がつかないので、影に加えて輪郭を付けます（「影だけだと区別がつかないので、影に加えてアウトラインが必要だと思います。」、[ADR-0024](./adr/0024-neutral-button.md)）。輪郭は、1px の `--color-surface-line`（`#DEE0E1`、細い境界線と同じ色）です。【決定】（[ADR-0025](./adr/0025-surface-button-line.md)）

よりはっきりした 3:1 の輪郭（`--color-line-strong`）も選べます。アプリ側で `--color-surface-line` を差し替えると、その範囲の白いボタンの輪郭が変わります。ユーザーのメモは「ものとしては A がこのみです。Bだと極端に浮き出ているように見えました。D も選択肢としてはありで、選べるようにしてもいいと思いました。」でした。

**お知らせ（Notice）には影を付けません。** お知らせは押せないためです。操作の場所に置く白いボタンだけ、ボタンなので影と輪郭があります。塗りのお知らせ（`appearance="filled"`）も同じで、白地との比が 1.20:1 の黄色の塗りにも、縁（影の輪郭）を付けません。【決定】（[ADR-0043](./adr/0043-notice.md)）

**例外: 浮かぶ UI（いまは Select の選択肢）の影は、押せることではなく、ページの上に重なっていることを表します。** 白い面に、白いボタンと同じ 1px の輪郭（`--color-surface-line`）と、やわらかい影（`--shadow-select-popup`）を付けます。【決定】（[ADR-0036](./adr/0036-select-popup.md)）

- 影の意味を「押せる」と「重なっている」に分けます。上の【固定】の規則は、押せる部品の影の規則として残します
- 影があると、選択肢が下の文章に重なっていることがいちばん分かります。影があるので、輪郭は淡い色でも境目が分かります
- Select のボトムシート（[ADR-0037](./adr/0037-select-sheet.md)）も浮かぶ UI です。シートの上向きの影と、長い選択肢の上下の端に付ける内側の影（続きがあることの印）も、押せることは表しません
- 影のトークンは、いまは Select の選択肢だけのものです。Menu・Popover など、ほかの浮かぶ UI でも同じ影を使うかは、それぞれを作るときに決めます

原則1は前半のはじめに決めたもので、浮かぶ UI まで考えて決めたものではありませんでした。ユーザーのメモは「原則1もかなり最初の方に決めたので、例外があってもいいなあとは思います。」と、最後の「E1 でよさそう。」でした。

**Disabled では、どの部品も影をなくし、本体の見た目も変えます。** 色を持つ部品は色を残して薄くし、色を持たない部品（入力欄、グレーのボタン・グレーのトグル・グレーの枠線のボタン）は明るいグレーにします。【決定】（[ADR-0026](./adr/0026-disabled.md)、[ADR-0029](./adr/0029-disabled-refine.md)）

| 部品                                                         | Disabled の見た目                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 色のボタン・白いボタン・色のトグル（青・ピンク）             | 本体を 40% に薄くする。色は残す。ただし、押せない OFF のトグルは、トラックを明るいグレー（`--color-switch-off-disabled`）にする                                                                                                                                               |
| 入力欄・グレーのボタン・グレーのトグル・グレーの枠線のボタン | 明るいグレーの塗り（`--color-field-disabled` / `--color-neutral-disabled`）に薄い文字（`--color-on-neutral-disabled`）。40% に薄くはしない。トグルは ON も OFF も、トラックを明るいグレー、ノブを薄い文字の色にする。枠線のボタンは、枠線を残して文字だけを薄い文字の色にする |
| ラベル・キャプション                                         | 変えない。「変更できません」などの説明が読めるままにする                                                                                                                                                                                                                      |

ユーザーのメモは「D ですね。例外として、グレーボタンの disabled はB（背景色と文字色の色が近くなる）がいいと思いました。」でした。以前は「Disabled は色を薄くする必要がない（影がないこと自体が『押せない』の表現）」としていましたが、スイッチ OFF と区別しにくいため、見た目を変える方向（[ADR-0011](./adr/0011-switch-off-track.md)）で比べ直しました。

Disabled を影だけで表さなくなったため、原則2との矛盾（グレー塗り・影なしの入力欄が、上の表では「押せない」と読める）は解消しました（[ADR-0026](./adr/0026-disabled.md)）。

**グレーの部品は、押せるときも押せないときも、グレーのボタンと同じ組み合わせにします。** 押せるときはグレーのボタンの塗り（`--color-neutral`）、押せないときは明るいグレーと薄い文字の色（`--color-neutral-disabled`、`--color-on-neutral-disabled`）です。【決定】（[ADR-0029](./adr/0029-disabled-refine.md)）

- 押せる OFF のトグルのトラックも、入力欄のグレーから、グレーのボタンの塗りに変えました（`--color-switch-off`）
- 押せないグレーのトグルは、グレーのボタンの「塗りと文字」を、そのまま「トラックとノブ」に写した形です
- 押せない OFF のトラックは、押せる OFF より少し濃く見えます。グレーのボタンと同じ関係です。押せるかどうかは、ノブの影と色で見分けます
- OFF のトグルにほんのり枠を付ける案と、押せない枠線のボタンの枠線を太くする案も比べましたが、採りませんでした

以前は、押せないトグル（特に OFF）と押せないグレーの枠線のボタンも 40% に薄くしており、ほとんど見えませんでした（[ADR-0028](./adr/0028-default-color.md)）。ユーザーのメモは「gray disabled switch ですが、選択できないときは無効なボタンと同じ色合いにできますか？」と、最後の「H でよさそう。」でした。

**送信中（loading）のボタンは、押せないボタンと同じ見た目にし、送信中の印だけを薄くせずに出します。** 「いまは押せない」を、Disabled の規則で伝えます。【決定】（[ADR-0034](./adr/0034-loading.md)）

- 印は3つから選べます。既定は、ラベルを 55% に薄くして回る円を重ねる形（`overlay`）です。ラベルの左に回る円を出す形（`inline`）と、下端に線を流す形（`bar`）も選べます
- 印は薄くしません。回る円は元の文字の色、流れる線はボタンの濃い色（色のボタンでは塗りの色）です。印まで薄くすると、止まっているのか進んでいるのかが分かりにくくなるためです
- 押せない見た目へは、押下と同じ緩急で 0.2 秒で切り替わります（`--duration-loading`）。出るときも戻るときも同じです
- 送信中は、押しても何もせず、hover と押下の反応もありません。フォーカスは外しません

ユーザーのメモは「loading 中は一律で disabled と同じ見た目にする」「スピナーやバーには disabled の見た目を適用しない」と、最後の「0.2 の F1 かなと思いました！」でした。

**入力欄と Select の待っているあいだ（loading）は、止める形（`loadingBehavior="blocking"`）と止めない形（`"non-blocking"`）から選べます。既定は止めない形です。** 待つ場面は、入力した値を確かめているとき（ユーザー名が使えるか）、選択肢を読み込んでいるとき（都道府県を選んだあとの市区町村）、フォーム全体を送っているときです。【決定】（[ADR-0042](./adr/0042-field-loading.md)）

| 止め方                        | 見た目と動き                                                                                                                                                                                                                                                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 止めない（`non-blocking`、G） | 書き換えられる。TextField は右端（suffix の前）に回る円。Select はふだんのプレースホルダ（「選んでください」）をすぐ出し、開ける。開くと、選択肢の下に「読み込んでいます」の行（回る円＋文。選べない）が出る。回る円は ▼ の左に 8px 空けて置き、▼ は替えない                                                               |
| 止める（`blocking`、E）       | 押せない欄と同じ見た目（`--color-field-disabled`・`--color-on-field-disabled`）で、書き換えられず、Select は開けない。Select は、プレースホルダの場所に「読み込んでいます」をプレースホルダと同じ色（`--color-fg-subtle`）で出し、▼ を隠して、回る円を ▼ のあった場所に置く。読み込むと、ふだんのプレースホルダと ▼ に戻る |

- **止めるときは、ボタンの送信中と同じく、Disabled の規則で「いまは触れない」を伝えます。** 印は薄くしません。フォーカスは外さず、フォーカスの青とエラーの赤の枠線も残します（[原則2](#2-状態は枠線で表す)）
- **止めるときの ▼ は隠します。** 開けないことを、▼ がないことで伝えます。止めないときは ▼ を残し、開けることを伝えたまま回る円を左に足します
- 印は回る円が既定（`loadingIndicator="spinner"`）で、下端（枠線の内側）に流れる線（`"bar"`）も選べます。止める形・止めない形のどちらでも選べます。回る円は ▼ と同じ `--color-fg-muted`、線は本文の色の 60% で、速さはボタンと同じです
- 読み込む前の Select は、いまと同じく押せない欄にし、プレースホルダの場所に理由（「先に都道府県を選んでください」）を出します。「読み込んでいます」の文は `loadingText` で変えられ、止めるときはプレースホルダの場所に、止めないときは読み込み中の行に出ます
- **押せない欄で、プレースホルダの場所に出す文と ▼ は `#6E787D` にそろえます。** ふだんのプレースホルダ・押せないときの理由（「先に都道府県を選んでください」）・止めるときの「読み込んでいます」は `--color-fg-subtle`、押せない Select の ▼ は `--color-select-icon-disabled`（同じ色。押せない塗りの上で 3.51:1）です。押せない文字の色（`--color-on-field-disabled`、`#A3A5A6`）は、選んだ値・入力した値だけに使います。値が入った押せない欄と、文を出している押せない欄を見分けるためです。以前の ▼ は `--color-fg-muted`（`#525C60`）のままでした
- 押せない Select の ▼ は、`disabledIcon="hide"` で隠せます。止める形・止めない形のどちらでも使えます
- 既定を止めない形にしたのは、打っている途中で入力を止めないことを優先するためです。止めるのは、使う側が場面に合わせて選びます
- **止めているあいだも、suffix のボタン（`FieldAddonButton`）は押せ、見た目もふだんのままです。** 止めるのは値の書き換えです。suffix のボタンは、パスワードの表示・非表示のように欄そのものを操作するものに限っていて（[原則8](#8-入力欄の様式は編集できるかで決まる)）、値を変えません。押せなくなるのは、欄の `disabled` のときだけです

ユーザーのメモは「ブロッキングの場合はEで、ノンブロッキングの場合はGで。」「どちらも共通で、ローディング前の disabled の時に下向き三角を非表示にできる（デフォルトはdisabledテキストカラーで表示）ようにしたいです。」「loading は、スピナーがデフォルトで行きます。」と、後から来た「既定はGでおっけーです。」「なるほど、disabled な選択肢と、選択済み選択肢が disabled な場合で区別がつかなくなる可能性があるのですね。すべて 6E787D に揃えたいです。」「待っている間も suffix は押せていいと思います」でした。

**動きを減らす設定（`prefers-reduced-motion: reduce`）では、回る円は3秒で1周にゆっくり回し、線は流さずに幅いっぱいに引いて明滅させます。回る円がふわっと出る動きはなくし、すぐに出します。** ボタン・入力欄・Select の読み込み中の行の、すべての印に当てます。【決定】（[ADR-0042](./adr/0042-field-loading.md)）

- 回る円は小さな動きなので、止めずにゆっくりにして、待っていることを伝え続けます（`--animate-spin-reduced`）
- 線は幅いっぱいを横切る大きな動きなので、その場の明滅（濃さ 60% ↔ 20%、1.6 秒で1往復）にします（`--animate-loading-bar-reduced`）
- ふわっと出る動き（`--animate-loading-in`、ふだんは 0.2 秒）は、設定がオンなら `none` にします。濃さだけの小さな動きですが、要らないためです。いまこの動きを使うのはボタンの印（`overlay`）だけで、入力欄の回る円と Select の読み込み中の行には、もともとありません
- 色の移り変わりは、これまでどおり止めます

ユーザーのメモは「動きを減らす設定は、円はAのゆっくり案、バーは明暗かなと思いました。」と、後から来た「動きを減らす設定ではふわっとでる動きはなしでよいです」でした。

階層や奥行きは、影ではなく**面の明度差と余白**で作ります。カードが浮いて見えるのは影のためではなく、背景より明るい面だからです。【固定】

ただし、浮かぶ UI（いまは Select の選択肢）は、この規則でも例外です。ページの上に重なるので、面の明度差だけでは下の内容と分けられません（上の「例外」、[ADR-0036](./adr/0036-select-popup.md)）。

影の値は、輪郭程度のごく薄い影に決まりました。hover では落ち影が消えて輪郭の 1px の線だけが残り、押下でもこの線は残します（`--shadow-raised`、`--shadow-raised-hover`、`--shadow-raised-press`）。【決定】（[ADR-0006](./adr/0006-button-shadow.md)、[ADR-0033](./adr/0033-press-edge.md)）押したとき、白いボタンは輪郭（`--color-surface-line`）と影の輪郭の線、グレーのボタンは影の輪郭の線が残るので、どちらも縁が消えません（[原則3](#3-hover-は一段沈む)）。

## 2. 状態は枠線で表す

このシステムで最も特徴的な規則です。一般的な「濃くする／薄くする」方式は使いません。

フォーム部品の場合:

| 状態       | 表現                                                                        | 印                                                       |
| ---------- | --------------------------------------------------------------------------- | -------------------------------------------------------- |
| 通常       | グレー塗り（`--color-field`）・枠線なし                                     | 【固定】                                                 |
| フォーカス | グレー塗りのまま + 2px の青の枠線（`--color-focus`）                        | 【決定】（[ADR-0019](./adr/0019-field-focus-change.md)） |
| エラー     | 淡い赤の塗り（`--color-field-invalid`）+ 2px の赤の枠線（`--color-danger`） | 【決定】（[ADR-0021](./adr/0021-field-error-fill.md)）   |

フォーカスでは塗りを変えず、枠線だけを足します。以前は「グレーの塗りが白に変わり、同時に枠線が付く」（塗り ⇄ 枠線の入れ替え）でした。ラウンド1のメモ「グレー背景から一気に白になってフォーカスリングが付くのはちょっとアニメーションとして大きすぎる」を受けて比べた結果、変わるものを枠線の1つに絞りました（[ADR-0019](./adr/0019-field-focus-change.md)）。

- **変化を小さくするときは、変わるものの数を減らします。枠線を細くはしません。** 枠線は 2px です（「枠は1px だとちょっと細すぎますね」）
- **状態の移り変わりは速くします**（`--duration-field: 100ms`）。ゆっくり変わると、操作できるまでのラグに見えます（「ゆっくりだとちょっと操作できるまでにラグがあると思っちゃいそう」）
- **変化の大きさは、知らせたい強さに合わせます。** フォーカスは操作のたびに起こるので枠線だけを足し、エラーは見落とされると困るので枠線と塗りの2つで知らせます（[ADR-0021](./adr/0021-field-error-fill.md)）。淡い赤とグレーの塗りは明度がほぼ同じ（1.01:1）で、変わるのは色相だけです

エラーでは、塗りも淡い赤に変えます（[ADR-0021](./adr/0021-field-error-fill.md)）。参照画像（`references/component-text-fields.webp`、`references/component-selects.webp`）のエラーはグレーの塗りのまま赤い枠でしたが、並べて比べた結果です（「A になじみがありましたが、こう見ると B の方がいいですね」）。

状態は枠線で表し、エラーでは色相でも知らせます。明度を変えて状態を表すことは**しないでください**。ただし hover は状態ではなく手応えなので、明度で表してかまいません（[原則3](#3-hover-は一段沈む)、[ADR-0022](./adr/0022-field-hover.md)）。平らなボタンの hover は、要素の文字と同じ色を淡く敷き、新しい色相は持ち込みません（[ADR-0027](./adr/0027-flat-press.md)）。

ボタン・リンク・トグルの場合は、キーボード（Tab キー）で操作したときだけ、2px の青い線（`--color-focus-ring`、入力欄の枠線と同じ `--color-focus`）を、輪郭から 2px 離して描きます。クリックやタップでは出しません（`:focus-visible`）。【決定】（[ADR-0031](./adr/0031-focus-visible.md)）

- **フォーカスは 2px の青い線で揃えます。** 部品の色によらず1色です（例外は、下の塗りのお知らせの中）。白地との比は 4.53:1 で、部品の基準（3:1、[原則12](#12-色は面用と前景用の2段で持つ)）を満たします
- **2px 離します。** 線を部品ではなく地の色と比べることになるので、青いボタンやピンクのボタンでも線が溶けません
- **動くのは線の色だけです。** 入力欄の枠線と同じ 100ms（`--focus-ring-duration`）でフェードインし、位置は動かしません。外から寄る動きも比べましたが、採りませんでした
- **入力欄は、上の表の枠線のままです。** クリックでもキーボードでも出ます
- **例外: 入力欄の suffix のボタンにキーボードでフォーカスしているあいだは、欄の青い枠線を消し、ボタンの線だけにします。** エラーの赤い枠線は残します（[原則8](#8-入力欄の様式は編集できるかで決まる)、[ADR-0040](./adr/0040-field-addon-rest.md)）
- **例外: 塗りのお知らせ（`<Notice appearance="filled">`）の中では、リンク・ボタン・× の線を、お知らせの文字の色（白か濃紺）にします。** 青い線は、情報・成功・危険の塗りの上で 1.00〜1.48:1 しかなく、見えないためです。警告の黄色の上は青でも 3.76:1 ありますが、ほかの塗りとそろえて濃紺にします。淡い面（既定）と枠線のお知らせの中は、青のままです（淡い面の上で 4.00〜4.08:1）。線の太さ・隙間・動きは変えません（[原則6](#状態の色とお知らせ)、[ADR-0043](./adr/0043-notice.md)）
- 文字のリンクは、線が角丸に沿うよう、角を 6px にしました（`--link-text-radius`）

ユーザーのメモは「いくつか比較しましたが B でよさそうです。」でした。線の青は、白地や明るいグレーの地を前提にしています。

## 3. hover は「一段沈む」

すべてのインタラクティブ要素に共通する上位規則です。要素の種類によって表れ方が変わります。【固定】

ただし、この原則は限られた素材（参照画像）から作ったため、例外がありえます（「原則3は限られた素材から作ったので、例外があるかもしれないですね」）。文字のリンクは、hover で背景を敷きません（[ADR-0027](./adr/0027-flat-press.md)）。代わりに、下線だけを濃くして反応します（[ADR-0030](./adr/0030-text-link.md)）。

| 要素                               | hover                                                         | 押下                                                  | 印                                                                                    |
| ---------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 影のある要素                       | 影が減る（落ち影が消え、輪郭の 1px の線だけが残る）           | 影は hover のまま（輪郭の線は残す）、1px 沈む         | 【決定】（[ADR-0033](./adr/0033-press-edge.md)）                                      |
| 平らな要素（入力欄）               | 塗りが半段濃くなる（`--color-field-hover`）                   | —（押すとフォーカスに移る）                           | 【決定】（[ADR-0022](./adr/0022-field-hover.md)）                                     |
| 平らな要素（枠線のボタン・リンク） | 文字の色を 8% 敷く（`--color-flat-hover`）                    | 文字の色を 16% 敷き（`--color-flat-press`）、1px 沈む | 【決定】（[ADR-0027](./adr/0027-flat-press.md)）                                      |
| 平らな要素（文字のリンク）         | 背景を敷かず、下線だけ濃くなる（淡い下線 → 文字より濃い下線） | 背景を敷かず、1px 沈む                                | 【決定】（[ADR-0027](./adr/0027-flat-press.md)・[ADR-0030](./adr/0030-text-link.md)） |

**hover は状態ではなく手応えです。** 状態（フォーカス・エラー）は原則2のとおり枠線と色相で表しますが、hover はマウスを載せたことへの反応なので、明度で表してかまいません。変化は状態より小さくします。入力欄の変化は、弱いほうから次の順です。

| 何が起きたか       | 変わり方               |
| ------------------ | ---------------------- |
| hover（手応え）    | 塗りが半段濃くなる     |
| フォーカス（状態） | 2px の青い枠線を足す   |
| エラー（状態）     | 赤い枠線＋淡い赤の塗り |

ユーザーのメモは「hover は状態ではなく手応えという原則に揃えてよいです。変わり方は B で。」でした（[ADR-0022](./adr/0022-field-hover.md)）。

**押しても、輪郭の 1px の線は残します。** 押下で消えるのは落ち影だけです（`--shadow-raised-press`）。白地に近い塗りのボタン（グレーのボタン、`#EFF0F1`）では、この線が縁の役目もしています。押して線まで消すと、縁が1周内側に下がり、ボタンが縮んだように見えます。【決定】（[ADR-0033](./adr/0033-press-edge.md)）

- **hover と押下は、1px 沈むことで見分けます。** 落ち影は hover の時点で消えているので、hover と押下の影は同じです
- グレーのボタンにも、ほかの塗りのボタンと同じ影を当てます。枠線は付けません

以前は「影を完全に消すのは押下に取っておいてください。hover で消してしまうと、押下との区別がつきません。」（【固定】）としていました。後半の軸 14 を比べている途中で、ユーザーが「グレーの方は小さくなる挙動も入っているように見えます」と気づいたため、軸に戻して比べ直しました（後半の軸 15）。グレーのボタンに枠線を付ける案や、輪郭の線を外す案も比べましたが、採りませんでした。ユーザーのメモは「枠線の追加はちょっと重すぎますね」と「一旦 A で進めます。」でした。「一旦」なので、使ってみて違和感があれば見直します。

**hover に枠線を使ってはいけません。** 枠線は原則2でフォーカスに割り当てられており、役割が衝突します。【固定】

**タッチ環境では hover が存在しません。** 指で操作するときは、押下時の変化を hover 以上にはっきり付けてください。【固定】

押下の動きは、100ms で素早く 1px 沈み、弾ませません（`--duration-press`、`--ease-press`、`--press-depth`）。【決定】（[ADR-0009](./adr/0009-press-motion.md)）影の値は [ADR-0006](./adr/0006-button-shadow.md)、押したときの影は [ADR-0033](./adr/0033-press-edge.md) で決まっています。

**平らなボタンと枠線のリンクは、要素の文字の色を淡く敷きます。** 青いボタンは淡い青、ピンクの More は淡いピンクになります。新しい色相を持ち込まないので、原則2とぶつかりません。押下では、塗りのボタンと同じく 1px 沈みます（`--flat-press-depth`）。押下の塗りは hover の2倍の濃さで、さらに沈むので、hover のない指の操作でも押したことが分かります。【決定】（[ADR-0027](./adr/0027-flat-press.md)）

- **文字のリンクには背景を敷きません。** 文字のリンクは文章の中にあるので、背景が出ると目立ちすぎます。押下では 1px 沈むだけです
- **文字のリンクは、hover で下線だけが濃くなります。** ふだんは文字の色を 35% に透かした淡い下線（`--color-link-underline`）で、hover では文字の色に黒を 30% 混ぜた、文字より濃い下線（`--color-link-underline-hover`）に 200ms で移ります（`--link-grow-duration`、`--link-grow-ease`）。文字の色は変えません（`--link-hover-darken: 0%`）。ふだんの下線が淡いので、文章の中でリンクが目立ちすぎません。【決定】（[ADR-0030](./adr/0030-text-link.md)）

ユーザーのメモは「D ですね。（リンクは今のように色はつかなくても良さそうです。）」と「ん、リンクのホバー背景色はそもそも無しでお願いしたいです。」でした。最初は1つ目のメモを「文字のリンクは灰色にする」と受け取りましたが、2つ目のメモで、背景そのものを敷かないことになりました（[ADR-0027](./adr/0027-flat-press.md)）。

文字のリンクの hover は、下線が太くなる案（動きを付けた案を含む）、下線なし、文字も濃くする案とも比べ、「G2 が結構好みです。一旦これで行きましょう」で決まりました。「一旦これで」なので、使ってみて違和感があれば見直します（[ADR-0030](./adr/0030-text-link.md)）。

## 4. すべての要素は「ラベル / 本体 / キャプション」の3層

ボタンにもキャプションが付きます。これは例外ではなく既定です。【固定】

- ラベル: 太字、本体の上
- 本体: コンポーネント
- キャプション: 小さくグレー（`--color-fg-subtle`）、本体の下。入力欄のヘルプテキストは、既定で本体の上（下の【決定】）

キャプションは省略可能ですが、**省略された場合でもレイアウトが崩れない**ように実装してください。

**入力欄のヘルプテキスト（キャプション）は、既定で本体の上に置きます。`captionPlacement="bottom"` で本体の下にも置けます。エラーと警告はキャプションを消さず、アイコン付きの行として下に足します。** 【決定】（[ADR-0041](./adr/0041-caption-and-message.md)）

| 並び      | `captionPlacement` | 上から順に                                  |
| --------- | ------------------ | ------------------------------------------- |
| 既定（F） | `top`              | ラベル → キャプション → 本体 → エラー・警告 |
| F′        | `bottom`           | ラベル → 本体 → キャプション → エラー・警告 |

- **入力欄のヘルプテキストは、ボタンのキャプションとは別のものとして扱います。** 参照画像のボタンのキャプションは、ボタンの下に中央寄せで置かれています。入力欄のヘルプテキストは左寄せです。そのため、本体の上に置いても、この原則の例外ではありません。ボタンのキャプションは、本体の下のままです
- **キャプションは、エラー・警告のあいだも消しません。** 入力の決まり（「8文字以上で、英字と数字を含めます」など）を読みながら直せます。以前は、エラーがキャプションと入れ替わり、同じ場所に出ていました
- **エラー・警告の行は、アイコン＋文です。** F では本体のすぐ下、F′ ではキャプションの下に出ます。エラーは丸の「!」と `--color-danger`（`#BA012D`）、警告は三角と `--color-fg-warning`（`#727200`）で、色だけでなく形でも見分けます。アイコンはキャプションの行の高さと同じ 16px（`--field-message-icon-size`）、文との間は 4px（`--field-message-gap`）で、線は Regular です（[ADR-0018](./adr/0018-icon-weight-by-context.md)）
- エラーの欄は、赤い枠線と淡い赤の塗りのままです（[原則2](#2-状態は枠線で表す)）。警告は送信を止めないので、欄の見た目を変えません
- **エラーと警告を両方渡したときは、両方を出します。** エラーの行、その下に警告の行です（F′ でも、キャプションの下にエラー、その下に警告）。行の間は、キャプションと本体の間と同じ `--space-field-gap`（指用 8px・マウス用 6px）です。以前は、エラーだけを出していました。ユーザーのメモは「エラーと警告が両方あるなら、両方出したいですね」でした（[ADR-0041](./adr/0041-caption-and-message.md) の追記）
- エラー・警告が出ても、本体とキャプションは動きません（F・F′ とも）。行は高さと濃さを 0.2 秒（`--duration-field-message`、緩急は `--ease-press`）で開き、閉じます。下の内容は、出た行の分（1行で指用 24px・マウス用 22px、2行で 48px・44px）跳ばずに滑ります。エラーと警告は行ごとに箱を持ち、別々に開き閉じます。エラーから警告に替わるときは、エラーの行が閉じて警告の行が開くので、下の内容は動きません。動きを減らす設定では、すぐ切り替わります（[ADR-0044](./adr/0044-message-announce.md)）
- 読み上げの説明は、見た目の順です。キャプション → エラー → 警告の順で、文字の prefix・suffix があるときはその前に来ます（[原則8](#8-入力欄の様式は編集できるかで決まる)）
- Select のボトムシートの見出しは、ラベル → キャプション → 欄のエラー → 警告の順です。行は本体の下と同じ形（アイコン＋文）で、キャプションとの間も、行どうしの間も 4px です。見出しはこれまでどおり読み上げでは隠し、選択肢の一覧（listbox）の説明に、キャプション → エラー → 警告の順でつなぎます。浮かぶ選択肢には欄の文を出しません（[ADR-0044](./adr/0044-message-announce.md)。下の Select の【決定】）

ユーザーのメモは「ヘルプテキストは上下を選べる（デフォルトは上、選択肢として下強制も選べる）が個人的には好みです。」「原則4ですが、元イメージのボタンキャプションはセンタリングされており、今回のキャプションは左寄せになっているという違いがあります。なので、許容する認識です。」と、最後の「F または F' を選べる形にしましょう！デフォルトは F とします。」でした。

**エラー・警告の行は、欄を離れたときやあとから確かめたときは、読み上げで polite に知らせます（A）。送信したときは、`<Form>` がエラーのある最初の欄へフォーカスを移します（E。既定）。`<Form errorSummary>` なら、フォームの上にエラーの一覧を出し、一覧へフォーカスを移します（C。長いフォーム向け）。** 【決定】（[ADR-0044](./adr/0044-message-announce.md)）

- 行は、いつも置いた箱（`aria-live="polite"`）の中に出します。いまの読み上げが終わってから読みます。エラーも警告も同じです
- 送信したときは、最初の欄（見た目の順）へ移り、入力した文字を選びます。欄の名前・無効・説明（キャプション → エラー）が読まれるので、ほかに何もいりません
- 一覧は、危険のお知らせ（`soft`、[原則6](#状態の色とお知らせ)）の見た目です。題は「入力を確かめてください（N件）」、本文は各欄へのリンクです。リンクの文は「欄の名前: エラーの文」です（例「パスワード: 数字が入っていません」）。欄の名前はその欄のラベルの文字で、名前もエラーの文も同じ太さ（400）です。項目の間と、題と最初の項目の間は `--space-field-gap`（指用 8px・マウス用 6px）です。`role="group"` で、フォーカスが移ったときに1回だけ読みます。欄のエラーに合わせて直り、すべて直すと閉じます。警告は入れません
- 送信で出た行は知らせません（箱を `aria-live="off"` にする）。フォーカスの移る先で読むので、同じ文を2回聞かないためです
- 欄を離れた直後にエラーだけ割り込む形（`role="alert"`）は採りませんでした。移った先の欄の名前が聞こえなくなるためです
- いつ何を確かめるかは、アプリが決めます。`<Form>` は、送信で出たエラーが描かれたあとで、フォーカスを移すだけです

ユーザーのメモは「内容の動きは B が好みです。」と「27 については、お勧めいただいたものを実装してみてもらってもいいですか？ C のケースも選べるようにはしたいかもですね。」でした。一覧の欄の名前と項目の間は、後から来た「errorSummary にエラーの項目名は欲しいかも。あと、エラー間の間隔がかなり狭いので、ちょっと広げたいですね」を受けて足しました。一覧の見た目・直すたびに減ること・題の文・フォーカスを最初の1件に移すこと・行の動きの 0.2 秒は、後から確かめてもらいました（「errorSummary の見た目は危険のお知らせでOKです。また直すたびに減って OK です。」「errorSummary のテキストは問題なさそう。」「フォーカスは最初の1件でいいと思います」「0.2 秒で良さそう」）。`<Form>` は Base UI の Form を包まない自前の部品です。「自前の form についてはあとからブラッシュアップをするので、一旦おｋです」なので、一旦この形にし、あとで見直します。

**Select では、選べない選択肢を選べなくし、理由をラベルの下の2行目に出します。選べるが知っておくことがある選択肢には、警告の2行目を付けます。欄のエラー・警告は、シートの見出しのキャプションの下にも出します。** 【決定】（[ADR-0044](./adr/0044-message-announce.md)）

- 選べない選択肢（`items[].disabled`）のラベルは、押せない文字の色（`#A3A5A6`、`--color-on-select-item-disabled`）です。押しても選ばれず、マウスの hover では塗りません。矢印キーでは止まり、名前・使用不可・理由が読まれます。文字を打って探すときは飛ばします。キーボードで止まったとき（focus-visible）だけ、hover と同じ塗り（`#F2F4F4`）でいまの場所を見せます。この塗りは比べずに足したもので、後から確かめてもらいました（「薄い灰色の面で良さそう」）
- 2行目（`items[].note`）は、`kind: 'reason'`（選べない理由。`#6E787D`・`--color-select-item-reason`、アイコンなし）か `kind: 'warning'`（選べる。三角と `#727200`）です。文の大きさと行の高さはキャプションと同じで、2行目のある選択肢だけ上下 6px 高くなります（指用 52px・マウス用 48px）。名前はラベルだけで、2行目は説明として読まれます
- 選べない選択肢を1つの見出しにまとめる形は採りませんでした。選べない理由は、選択肢ごとに違うことがあるためです
- **部品は、渡された文をそのまま出します。** どの選択肢を選べなくするか、理由・警告・欄のエラーの文をどう書くかは、実装ガイドラインで決めます（部品では組み立てない）
- 選んだ選択肢の警告を欄の `warning` にも渡すと、シートでは、その選択肢の2行目と見出しの両方に出ます。部品は、欄の文が選択肢についての文かどうかを知りません。ユーザーは、これを自然なこととして受け入れました（「選んだ選択肢の警告がシートの警告に移るのは自然なことかなと思いました。」）。欄に渡すかどうかは、実装ガイドラインで決めます

ユーザーのメモは「27 は A が良さそうです。選択肢が選べない理由は複数あり、グルーピングは難しいと思いました。ただし、テキストの生成ロジックは、実装ガイドラインベースとし、コンポーネントレイヤーでは持たなくてよさそうです。」と「選べない選択肢は止まって読み上げて良さそうです。2と3は許容します。」でした（2は浮かぶ選択肢が本体の下の文を隠すこと、3は2行目の分だけシートが半分の高さで開くこと）。

## 5. 角丸は部品と包むもので分ける

| 対象                                   | 角丸                                                                                        | トークン                | 印                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------- |
| ボタン・入力欄（フォーム部品）         | 12px で統一。密度によって変えない                                                           | `--radius-control`      | 【決定】（[ADR-0008](./adr/0008-control-radius.md)）    |
| カード（標準・入れ子の型とも）         | 16px                                                                                        | `--radius-card`         | 【決定】（[ADR-0016](./adr/0016-card-radius.md)）       |
| 入れ子の型のカードの余白（画像の周り） | 8px。画像の角丸は同心で 8px                                                                 | `--card-nested-inset`   | 【決定】（[ADR-0014](./adr/0014-nested-card-inset.md)） |
| カードの画像の比率                     | 16:9                                                                                        | `--card-media-aspect`   | 【決定】（[ADR-0017](./adr/0017-card-media-aspect.md)） |
| リンク・タグ・トグルなどの小物         | 完全な pill                                                                                 | `--radius-pill`         | 【固定】                                                |
| 文字のリンク（文章の中）               | 6px。キーボードで操作したときのフォーカスの線が沿う角。背景を敷かないので、ほかには見えない | `--link-text-radius`    | 【決定】（[ADR-0031](./adr/0031-focus-visible.md)）     |
| 入力欄の prefix・suffix                | 外側の角は本体と同じ 12px、入力側は直角。内側に 4px 浮かせる形では、本体と同心の 6px        | `--field-addon-*`       | 【決定】（[ADR-0035](./adr/0035-field-addon.md)）       |
| Select のボトムシート（上の角）        | 16px（カードと同じ）                                                                        | `--select-sheet-radius` | 【決定】（[ADR-0037](./adr/0037-select-sheet.md)）      |
| お知らせ                               | 12px（部品と同じ）。余白も部品の寸法で、カードの 16px にはしない                            | `--notice-radius`       | 【決定】（[ADR-0043](./adr/0043-notice.md)）            |

ボタンと入力欄は同じ値に揃えます。角丸を高さに比例させる規則は採りません。密度を切り替えると見た目が変わり、揃えたいときに困るためです（「B のように比例する形式だと、ルックが揃えたくても見た目が変わって困ることありそう。」）。

**ボタンの見た目のリンクは、角 12px のボタンのままです。** Button が `<a>` を描くもの（`render`）で、見た目はボタンと同じなので、「リンクは pill」の例外ではありません。枠線のリンクは pill のままです。Link にボタンの見た目を持たせる案（角 12px のリンク）は、この原則の例外になるので採りませんでした。【決定】（[ADR-0046](./adr/0046-link-rest.md)、[原則7](#7-塗りか枠線かの使い分け)）

カードは2つの型に分けます。ラウンド2のユーザーのメモ「カードについては入れ子のタイプだとちょっと過剰カモ。このタイプも選べるようにするのであれば、下の角丸が丸すぎる気持ち。」を受けたものです。

- **標準のカード**: 画像を端まで届かせる
- **入れ子の型**: 画像を内側に角丸で収める型。利用者が選べる型として用意する。画像の角丸は、外側の角丸 − 余白（同心）

標準のカードと入れ子の型は、同じ角丸 16px を使います。ラウンド4のユーザーのメモ「角丸を通常版と入れ子版で変えるのはちょっとうーんという感じもしますが、画像の角丸に影響してくるので、入れ子の方が控えめの方がいいかもですね。」を受けて比べた結果、入れ子も 16（画像は 8）に決まりました（[ADR-0016](./adr/0016-card-radius.md)）。画像の比率は、どちらの型も 16:9 です（[ADR-0017](./adr/0017-card-media-aspect.md)）。

## 6. 水色はブランド、青は Primary、ピンクは Secondary

水色は構造の色で、見出しとロゴに使います。青（Primary）とピンク（Secondary）は、色を持つ部品（ボタン、スイッチ、タグ、リンクなど）で**利用者が選ぶ色**です。利用者が色を指定しないときは、グレー（neutral）になります。

| 色     | 役割             | 面用（塗り・装飾）  | 前景用（文字・枠線・白文字を載せる塗り） | 使いどころ                     | 印                                                    |
| ------ | ---------------- | ------------------- | ---------------------------------------- | ------------------------------ | ----------------------------------------------------- |
| 水色   | ブランド（構造） | `--color-brand`     | `--color-fg-brand`                       | ロゴ、見出し、セクションラベル | 【固定】                                              |
| 濃い青 | Primary          | `--color-primary`   | `--color-primary`                        | 利用者が選ぶ。フォーカス枠     | 【決定】（[ADR-0012](./adr/0012-primary-blue.md)）    |
| ピンク | Secondary        | `--color-secondary` | `--color-fg-secondary`                   | 利用者が選ぶ。用途を限定しない | 【決定】（[ADR-0013](./adr/0013-secondary-color.md)） |

- **Primary と Secondary に用途の区別はありません。** その場所に最も合う色を、コンポーネントの利用者が選びます（「ピンクの使いどころは、単に Secondary という立ち位置なので、限定されません。その場所に最も合う色をコンポーネントの利用者が選ぶことになります。」）。以前の「青が『進む』、ピンクが『寄り道』」「ピンクを主要アクションに使わない」は廃止しました
- **Primary の青は `#2474DF`** です。一旦この値で確定しており、後で見直してかまいません（「Primary は一旦これで。」）。白地で 4.53:1 あるため、面用と前景用は同じ値です
- **Secondary の塗りに白文字を載せるときは、前景用の `--color-fg-secondary`（`#E41966`、白文字で 4.54:1）を使います。** 面用の `--color-secondary`（`#F53273`）は白文字で 3.76:1 しかないため、文字を載せない塗り（トグル ON など）に使います（[原則12](#12-色は面用と前景用の2段で持つ)）
- **利用者が色を指定しないとき（既定の色）、色を持つ部品はすべてグレー（neutral）です。** 塗りのボタンはグレーのボタン、枠線のボタン・リンクはグレーの枠線と文字、文字のリンクはグレーの文字（`--color-fg-muted`）、トグルの ON は濃いグレー（`--color-fg-muted`）になります。色は、部品ごとの `color`（`"primary"`・`"secondary"`・`"neutral"`。ボタンは `"danger"`・`"surface"` も、タグは状態の色の `"info"`・`"success"`・`"warning"`・`"danger"` も）で選びます。セクションごとにまとめて既定の色を変える仕組みは、必要になったら足します。【決定】（[ADR-0028](./adr/0028-default-color.md)）ユーザーのメモは「全部青がいいかなーと思っていますが、全部グレーの案も追加してみてもらえますか？」と「特に指定がない場合はグレーで良さそうです。」でした

水色の面に載せる文字は `--color-on-brand`（濃紺グレー）です。水色の前景用 `--color-fg-brand` は白地で 3.02:1 なので、大きい文字（見出し、セクションラベル）にしか使えません。

タグは、淡い面に同じ色相の濃い文字を載せる塗り方にします。【決定】（[ADR-0007](./adr/0007-tag-color.md)）ADR-0007 で決まったのはこの塗り方で、水色という色ではありません。タグの色は利用者が青・ピンク・グレーから選び、指定しないときはグレーです（[ADR-0028](./adr/0028-default-color.md)）。ユーザーのメモは「タグは青色で決まっているわけではなく、色の乗せ方がいいなと思ったところでした。primary なタグ、secondary なタグはある認識です。」でした。

**タグは、利用者が選ぶ色（青・ピンク・グレー）に加えて、状態の色（情報・成功・警告・危険）も持ちます。** 状態のタグの面と文字は、淡い面のお知らせ（`soft`）の面と題と同じ値です。`<Tag color="success">` のように使います。【決定】（[ADR-0038](./adr/0038-warning.md)、[ADR-0043](./adr/0043-notice.md)）

| タグ       | 種類           | 面                      | 文字                       | 面との比 |
| ---------- | -------------- | ----------------------- | -------------------------- | -------- |
| 青         | 利用者が選ぶ色 | `--color-tag-primary`   | `--color-on-tag-primary`   | 4.52:1   |
| ピンク     | 利用者が選ぶ色 | `--color-tag-secondary` | `--color-on-tag-secondary` | 4.54:1   |
| グレー     | 利用者が選ぶ色 | `--color-tag-neutral`   | `--color-on-tag-neutral`   | 6.02:1   |
| 情報       | 状態の色       | `--color-tag-info`      | `--color-on-tag-info`      | 4.52:1   |
| 成功       | 状態の色       | `--color-tag-success`   | `--color-on-tag-success`   | 4.52:1   |
| 警告（黄） | 状態の色       | `--color-tag-warning`   | `--color-on-tag-warning`   | 4.55:1   |
| 危険       | 状態の色       | `--color-tag-danger`    | `--color-on-tag-danger`    | 5.93:1   |

- 状態のタグは、利用者が選ぶ色とは別です（下の「状態の色とお知らせ」）。情報のタグは青のタグのトークンを、成功・危険のタグは成功・危険の色を指します。値の層は足していません
- 寸法はほかのタグと同じです（文字はマウス用 11px・指用 12px、高さ 20px、pill）。面と白地の比も 1.11〜1.13:1 で、ほかのタグ（1.13〜1.14:1）と同じです
- **近い組み合わせがありますが、そのまま受け入れました。** タグは文言で見分けます
  - 情報のタグは、青のタグと同じ値です（「情報は前の色合いでよいです」）
  - 危険のタグの面は、ピンクのタグの面とほぼ同じです（色の差 0.6、比 1.01:1）。文字どうしは色の差 8.4 で、危険の赤のほうが暗く見えます（明度の比 1.29:1）
  - 成功と警告の文字（`#008132` と `#727200`）は、色相が 148° と 110° で違い、近いのは明度です（比 1.02:1、色の差 9.5。面どうしの色の差は 3.3）。2色覚（1型・2型）を真似ると、文字の色の差は 2.9〜3.7 に縮みます

ユーザーのメモは「状態のタグは欲しいです！」「情報は前の色合いでよいです」と、成功と警告の近さについての「成功と警告のいろ、そこまでちかいですか？これでいいかなと」でした。

タグの文字の青は、Primary の青（`--color-primary`）より少し濃くしています。Primary の青は、淡い青の面の上では 4.01:1 しかないためです。

### Danger と Secondary の区別

Danger は `#BA012D`（`--palette-red-700`）です。色相はそのままにして、明度を下げてピンクと区別します。【決定】（[ADR-0023](./adr/0023-danger-color.md)）

[ADR-0013](./adr/0013-secondary-color.md) でピンクの用途を限定しなくなったため、ピンクの塗りのボタンが削除ボタン（Danger）の隣に並ぶ場面がありえます。そのため、Danger とピンクを見分けられる必要があります。

Danger の値は2回変わりました。

- 前半: 旧値 `#EE4665` から `#D4283F` に変えました。理由は「旧値は Secondary `#F53273` と明度が近く、削除ボタンと More ボタンが隣り合うと区別できなかった」でした。ただし、実測した明度差は小さく、この根拠は弱いものでした
- 後半: `#D4283F` から `#BA012D` に変えました。色相（20.6°）は同じで、OKLCH の明度を 0.57 から 0.50 に下げています。前半でユーザーが示した方向性（「Danger はもうちょっと濃くしてもいいかも。」）に沿った決定です

| 組み合わせ                          | 変更前 `#D4283F` | 変更後 `#BA012D` |
| ----------------------------------- | ---------------- | ---------------- |
| ピンク（面用）`#F53273` と Danger   | 1.34:1           | 1.78:1           |
| ピンク（前景用）`#E41966` と Danger | 1.11:1           | 1.48:1           |
| Danger の塗りに白文字               | 5.03:1           | 6.71:1           |

区別は明度だけで付けます。色相、形、アイコンは使いません。色相を朱色に寄せる案（C `#BE260B`、D `#B12B00`）もありましたが、選びませんでした。

ユーザーは Storybook で A「濃く」を選びました（「選びました！エラーテキストも見やすいかなと思っています。」）。入力欄の下に出る赤いエラーの文字も、白地で 6.71:1 になり、読みやすくなります。

### Warning

警告（Warning）の黄色 `#EFF16B` は塗りに残し、上に載せる文字とアイコンは濃紺（`--color-on-warning`、11.49:1）にします。白地に置く文字・枠線・アイコンには、同じ色相で明度を下げたオリーブ色 `#727200`（`--color-fg-warning`、白地 5.09:1）を使います。【決定】（[ADR-0038](./adr/0038-warning.md)）

- 黄色は白文字で 1.20:1 しかなく、Danger と同じ使い方（色の塗りに白文字）はできません。色相を黄土に寄せて白文字を載せる案（`#9C6E01`）もありましたが、黄色から離れるので採りませんでした
- オリーブ色の文字は、黄色の塗りの上では 4.24:1 で基準に届きません。黄色の塗りの上は、いつも濃紺にします
- 黄色の塗りは白地との比が 1.20:1 です。グレーのボタンと同じく、影の輪郭（`--shadow-raised`）で縁を出します。ただし、お知らせは押せないので影を付けず、塗りのお知らせの黄色にも縁を付けません（[原則1](#1-影は押せることの記号)、[ADR-0043](./adr/0043-notice.md)）
- タグは、ほかのタグと同じ塗り方です。淡い黄色（`--color-tag-warning`、`#F3F5CE`）にオリーブ色の文字（`--color-on-tag-warning`、4.55:1）を載せます。`<Tag color="warning">` で使えます
- 入力欄の下の警告の文は、三角のアイコンと文をオリーブ色（`--color-fg-warning`）にし、欄の枠線と塗りは変えません。`<TextField warning="…" />` で使えます（[原則4](#4-すべての要素はラベル--本体--キャプションの3層)、[ADR-0041](./adr/0041-caption-and-message.md)）
- 警告の色のボタンは、いまは作りません。トークンはあるので、必要になったら Button の `color` に足します

ユーザーのメモは「warning については A でよさそうです。warning のボタンというのがそもそもあまり使うことは無いですが。」でした。

**警告のお知らせの既定は、淡い黄色の面です。** 面は `#F3F5CE`（警告のタグの面と同じ）、題とアイコンはオリーブ色 `#727200`（4.55:1）、本文は濃紺（12.34:1）です。黄色の塗りに濃紺の文字（ADR-0038 の形）は、塗りの見た目（`appearance="filled"`）として残ります。【決定】（[ADR-0043](./adr/0043-notice.md)）

- ADR-0038 では、お知らせを黄色の塗りに濃紺で組んでいました。ほかの状態の色とそろえて、淡い面を既定にしました（下の「状態の色とお知らせ」）
- 塗り・白地の文字・タグ・入力欄の下の警告の文の値は、ADR-0038 のままです
- お知らせ用の面・文字・アイコンの役割は、塗りのトークンと分けました（`--color-notice-warning`・`--color-notice-warning-title` など）。塗りのお知らせは、`--color-notice-warning-filled` が `--color-warning` を指します

ユーザーのメモは「warning の原則については、こちらに変更で良さそう。」でした。

### 状態の色とお知らせ

状態の色は、情報・成功・警告・危険の4つです。お知らせ（`<Notice>`）と、白地に置く文字・枠線・アイコンに使います。利用者が選ぶ青・ピンク・グレーとは別です。【決定】（[ADR-0043](./adr/0043-notice.md)）

**お知らせの見た目は、淡い面（`soft`）が既定です。濃い塗り（`filled`）と枠線（`outline`）も選べます。** 名前は、ボタンの `appearance`（`filled`・`outline`）にそろえました（後から「filled でいいですね」）。どの場面でどれを使うかは、使う側が選びます。

| 見た目（`appearance`） | 面と文字                                                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `soft`（既定）         | タグと同じ淡い面（[ADR-0007](./adr/0007-tag-color.md) の塗り方）。題とアイコンは同じ色相の濃い色、本文は濃紺 |
| `filled`               | 白文字が載る濃い塗り。警告だけは黄色の塗りに濃紺（上の「Warning」）。題・本文・アイコンは同じ色              |
| `outline`              | 白い面に 1px の状態の色の枠線。アイコンも枠線の色、題と本文は濃紺                                            |

| 色   | `soft` の面 | 題・アイコン（`soft`） | 本文（`soft`）  | `filled`                           | 白地の文字・`outline` の枠線とアイコン         |
| ---- | ----------- | ---------------------- | --------------- | ---------------------------------- | ---------------------------------------------- |
| 情報 | `#E9F2FE`   | `#196BD6`（4.52:1）    | 濃紺（12.23:1） | `#2474DF`（Primary）に白（4.53:1） | `#196BD6`（`--color-fg-info`、白地 5.10:1）    |
| 成功 | `#E5F8E7`   | `#008132`（4.52:1）    | 濃紺（12.44:1） | `#008132` に白（5.02:1）           | `#008132`（`--color-fg-success`、白地 5.02:1） |
| 警告 | `#F3F5CE`   | `#727200`（4.55:1）    | 濃紺（12.34:1） | `#EFF16B` に濃紺（11.49:1）        | `#727200`（`--color-fg-warning`、白地 5.09:1） |
| 危険 | `#FEEDED`   | `#BA012D`（5.93:1）    | 濃紺（12.20:1） | `#BA012D` に白（6.71:1）           | `#BA012D`（`--color-danger`、白地 6.71:1）     |

- **情報は Primary と同じ色相（青）です。** 値の層の Info（`#6B9FF1`）は Primary と色相が 1.7° しか違わないので、役割を当てません。情報の淡い面と文字は、青のタグと同じ値です
- **形は、アイコンの右に太字の題・本文・操作を縦に積み、× を右上に置きます。** 角丸は部品と同じ 12px です（[原則5](#5-角丸は部品と包むもので分ける)）。余白と文字は部品の寸法で、密度で変わります（余白は指用 16px・マウス用 12px、アイコンと文の間は 12px・8px）
- 操作（`actions`）には、白いボタン（`<Button color="surface">`）か文字のリンクを置けます。本文の下に 6px 空けて置きます。中のリンクは、`color` の指定によらずお知らせの文字の色になり、操作の場所では太字です（後から「お知らせの色合わせもよし」）
- アイコンは、情報が丸の「i」、成功が丸のチェック、警告が三角、危険が丸の「!」です。成功と警告の文字の色（`#008132` と `#727200`）は明度の比が 1.02:1 なので、アイコンの形で見分けます（タグでは文言で見分けます。上のタグ）
- お知らせには影を付けません（[原則1](#1-影は押せることの記号)）。塗りのお知らせの中のフォーカスの線は、お知らせの文字の色です（[原則2](#2-状態は枠線で表す)）。黄色の塗り（`filled` の警告）の中も、青でも 3.76:1 ありますが、ほかの塗りとそろえて濃紺（11.49:1）にします。後から「警告の色は外れてなければおまかせします。」とのことで、このままにしました
- 読み上げでは、題・本文・操作を role の箱に入れます。危険は `role="alert"`、ほかは `role="status"` です。× は箱の外に置き、「閉じる」と読みます。割り込む `alert` を急ぎの知らせ（危険）だけにするのは W3C と MDN の勧めに沿った形で、後から「危険だけ割り込みの件は、今おっしゃっていただいた形で良いです。」と確かめました（[ADR-0043](./adr/0043-notice.md) の追記）

ユーザーのメモは「25 については C がデフォルト、D も選べるようにしたいです。あと、お知らせの形で言及されていた、アウトラインタイプも選べたら嬉しですね。」と「お知らせの形は、めっちゃ A が好みです。C のようにボタンも置けるようにはしたいですが、余白類は A に揃える形で。」でした。

## 7. 塗りか枠線かの使い分け

- **既定**: 画面内で最も進めたい操作は塗り、それ以外は枠線【固定】
- **例外**: 密度の高い並び（カード内リンク、SNS アカウント一覧など）では、塗りが重すぎるため枠線に落とす【固定】

**枠線のリンク（More、SNS のアカウント一覧など）は、枠線のボタンと同じ寸法にします。** 高さ `--size-control`、文字 `--text-control`、左右の余白 `--space-control-x` で、どれも密度で切り替わります。押せる範囲は見た目と同じです。【決定】（[ADR-0039](./adr/0039-link-size.md)）

**文字のリンクは大きさを持ちません。** 置いた場所の文字の大きさと行の高さをそのまま使い、文章の外に単独で置いても同じです。押せる範囲も文字の行だけで、見えない広がりは付けません。広い範囲が要るときは、文字のリンクを広げず、ボタンを使います。ページを移るときは、下の「ボタンの見た目のリンク」を使います（[ADR-0046](./adr/0046-link-rest.md)）。【決定】（[ADR-0039](./adr/0039-link-size.md)）

参照画像の More と SNS のボタンは、文字が小さく横に長い pill です。小さくする案や横長の案も比べましたが、採りませんでした。ユーザーのメモは「枠線のリンクは枠線のボタンと同じ、現行版で構いません。」と「文字のリンクは現行版で良いです。領域に問題がある場合、ボタンを使う考えです。」でした。

**幅いっぱいに広げた枠線のリンク（SNS のアカウント一覧の2列など）は、文字とアイコンをまとめて中央に寄せます（`contentAlign="center"`、既定）。** 文字を左・最後のアイコンを右端に置く形（`"between"`）と、文字を箱全体の中央・最後のアイコンを右端に置く形（`"center-end"`）も選べます。【決定】（[ADR-0046](./adr/0046-link-rest.md)）

- 並べて文字の頭とアイコンを縦にそろえたいときは `between`、文字をボタンのように中央に置きたいときは `center-end`、1本だけで左右をつり合わせたいときは `center` です。どれを使うかは、使う側が選びます
- 寄せ方は、枠線のリンクだけに効きます。文字のリンクには効きません
- 幅が中身で決まるときは、`center` と `between` はいまと同じ見た目です。`center-end` は、左に「アイコン＋8px」の空き（マウス用 24px・指用 28px）を足して文字を中央に置くので、その分だけ広くなります。`center-end` は幅いっぱいで使います
- `between`・`center-end` では、入りきらない文字を「…」で切ります。`center` は切りません
- 並べるときは `between`、1本だけなら `center` と、部品が切り替える案は採りませんでした。使う側が選べるので、部品が「並べているか」を知らなくて済みます

ユーザーのメモは「26の幅いっぱいのリンクについては、A・B・C を全部選べるにしたいですね…」と「デフォルトは A でよさそう。」でした。

**ボタンの見た目のリンクは、Button の `render` に `<a href>` や Next.js の Link を渡して作ります。** 見た目は Button と同じで、要素だけが `<a>` になります。塗り・枠線、青・ピンク・赤・グレー・白のすべての見た目をリンクにできます。【決定】（[ADR-0046](./adr/0046-link-rest.md)）

- **見た目の定義は Button の1つだけにし、要素だけを替えます。** ボタンとの違いは「機能的に button がもとなのか a が元なのかだけ」です。角も 12px のままなので、「リンクは pill」の例外ではありません（[原則5](#5-角丸は部品と包むもので分ける)）
- **ボタンの見た目のリンクには、右上向きの矢印（↗）を必ず付けます。** ボタンと見分けるための印で、新しいタブで開くかどうかにかかわらず付けます。ラベルの後ろの最後に置き、飾りなので読み上げません。枠線のリンク（pill）のアイコンは、いままでどおり使う側が置きます（アイコンのない新しいタブのリンクだけ、部品が ↗ を付けます。下の「新しいタブで開くリンク」）
- **Next.js の Link に Link の見た目を重ねるときも、`render` を使います。** `<Link appearance="outline" render={<NextLink href="/works" />}>` と書きます。`<a>` のときは、いままでどおり Link に `href` を書きます。書き方は Base UI の部品の `render` と同じです
- `href`・`target` は渡す要素に書き、ラベルは Button・Link の children に書きます
- 新しいタブで開くとき（`target="_blank"`）は、`rel="noopener noreferrer"` を付けます（下の「新しいタブで開くリンク」）
- **リンクは送信中を持ちません。** `render` を渡したときの props は別の型（`ButtonLinkProps`）で、`loading`・`loadingIndicator`・`type` を書くと型のエラーになります。型を外して渡されたとき（JavaScript や `as`）は、無視して開発時に1回だけ警告します。ユーザーのメモは「ボタンの見た目のリンクは loading を受け取らないのが正しそうですね（リンク(nextlink, a)に loading という状態はなさそう）」でした

**キーボードはリンクのままにします。** Enter で移り、Space では移りません（Space はページのスクロール）。ブラウザのリンクの挙動で、見た目がボタンでも同じです。【決定】（[ADR-0046](./adr/0046-link-rest.md)）

**リンクにも押せない状態（`disabled`）を持たせ、押せないボタンと同じ扱いにします。** Button（`render`）と Link（文字・枠線）に `disabled` を渡すと、`href` を外し、渡した要素（Next.js の Link など）は描かず、`href` のない `<a role="link" aria-disabled="true">` を描きます。【決定】（[ADR-0046](./adr/0046-link-rest.md)）

- Tab では止まりません（`<button disabled>` と同じ）。読み上げのモードでは「リンク、利用不可」と読まれます。押しても、右クリックの「新しいタブで開く」も、何もしません
- ボタンの見た目のリンクは、`<Button disabled>` と同じ見た目です（[原則1](#1-影は押せることの記号) の Disabled）。↗ は残します
- **押せない文字のリンクは、ただの文字と同じ見た目にします。** 下線を引かず、色は周りの文字を受け継ぎます（色を指定していても）。カーソルも周りの文字と同じで、部品が付ける ↗ も付けません（新しいタブで開くリンクでも）。hover と押下でも変わりません。文字のリンクは色と下線で押せることを表すので、押せないときはその両方を外します。読み上げでは「リンク、利用不可」と読まれます
- 押せない枠線のリンクは、押せないグレーの枠線のボタンと同じ色（枠線 `#DEE0E1`・文字 `#A3A5A6`、カーソルは not-allowed）にし、↗ も残します。色（青・ピンク）を指定していてもグレーにします
- はじめは比べずに、文字のリンクも `#A3A5A6` の文字（下線は残す）にしていました。ユーザーのメモ「押せない文字のリンクはそもそも下線が引かれず、ただの文字と同じ見た目で。枠線のリンクは26の実装したリンクにあるものでよいです」を受けて、文字のリンクだけを変えました。色を残して 40% に薄くする形も採りません
- `href` を残して押したときに止める形と、`<button disabled>` に替える形は採りませんでした。前者は右クリックや先読みが動いたままで、後者は押せるかどうかで役割（link と button）が入れ替わります

**新しいタブで開くリンクには、読み上げに「（新しいタブで開きます）」を足します。** ボタンの見た目のリンク・文字のリンク・枠線のリンクのどれも同じです。↗ の付け方は、リンクの種類で分けます。【決定】（[ADR-0046](./adr/0046-link-rest.md)）

- ボタンの見た目のリンク: ↗ を必ず付けます（新しいタブかどうかにかかわらず）
- 文字のリンク: 新しいタブで開くときだけ、部品が文字の後ろに ↗ を付けます。大きさは文字より少し小さい 0.85em で、矢印の線の下端を文字の基線にそろえます（下寄せ）。線は Regular（[ADR-0018](./adr/0018-icon-weight-by-context.md)）。リンクの下線は ↗ の右端まで続き、位置・太さ・色も hover での変化も文字の下線と同じです。最後の語と一緒に折り返します。押せないときは付けません（下線もありません）
- 枠線のリンク: 使う側がアイコン（最後の子の要素。› でも ↗ でも）を置いたときは、それを使います。アイコンがない新しいタブのリンクには、部品が ↗ を付けます。同じタブで開くアイコンのないリンクには付けません

ユーザーのメモは「ボタンの形のリンク、ですが、枠線付きのリンクと同じ認識です。Nextjs などを使う可能性が大きいので、render を使わざるをいない可能性を感じていますが、どうでしょうか。」「26について、塗のボタンのリンクも欲しいです！リンクのものもボタン（onClick など）のものは見た目は同じです！（機能的に button がもとなのか a が元なのかだけ） Nextjs 対応はしたいので render のパターンでお願いします。」と「あ、ボタンの見た目のリンクの場合、右上向き矢印は必ず入る、という認識です。」でした。キーボードと押せないリンクのメモは「Entry と Space に関しては理解できました。このままでおっけーです。」「押せないボタンは読み上げられないのですか？」「おすすめしてもらったもので良さそうです。」、新しいタブのメモは「1はそのままでおっけーです。2は同じ形にしたいですね。文字のリンクの場合は、新しいタブのみ矢印アイコンを入れたいですが、枠線のリンクとはどれの話ですか？」と「ああー、理解しました。枠線のリンクはアウトラインボタンの見た目のボタンとほぼ似てますね。こちらはアイコンの指定があればそれを、指定がない新しいタブなら文字のリンクと同じ挙動で。」でした。文字のリンクの ↗ の大きさと下線は、あとのメモ「文字のリンクは、矢印のところまで下線を伸ばしてほしいです。また、ちょっとだけ矢印は小さくしてみてほしいです（下寄りでOK）」で決まりました。

「文字のリンクはどこで見れますか？」「枠線のリンクの中身が〜をアイコンと〜はどこで見れますか？」と聞かれたので、「実装したリンク」のストーリー（`design-review-26-link-rest--implemented`）に、「文字のリンク」の区画（同じタブ・新しいタブ・押せない・押せない新しいタブ・灰色の文の中）と、枠線のリンクの「子が1つだけのとき」（文字だけ・アイコンだけ・文字とアイコン × 同じタブ・新しいタブ）を足しました。

## 8. 入力欄の様式は「編集できるか」で決まる

| 用途                     | 様式                          |
| ------------------------ | ----------------------------- |
| 編集できる（フォーム）   | グレー塗り（`--color-field`） |
| 読み取り専用（情報表示） | 下線のみ（`--color-line`）    |

ユーザーから見ると「**下線が出てきたら読むだけ**」という判別規則になります。この対応を崩さないでください。【固定】

文字のリンクの下線は、この規則とは別です。文字の下にだけ引く淡い下線で、欄の幅いっぱいに引く読み取り専用の下線とは形が違います。「下線が出てきたら読むだけ」は、入力欄についての規則です（[ADR-0030](./adr/0030-text-link.md)）。

入力欄に付く prefix・suffix（入力欄と一体のラベルやボタン）は、グレー（`--color-field-addon`）にします。【決定】（[ADR-0024](./adr/0024-neutral-button.md)）ユーザーのメモは「入力欄の suffix, prefix のような物であればグレーになっている必要があると思います。」でした。

**prefix・suffix は、文字もボタンも、入力欄の端に接した塊にします。** 【決定】（[ADR-0035](./adr/0035-field-addon.md)）

- 外側の角は本体と同じ 12px、入力側の角は直角です。フォーカスとエラーの枠線は、塊の外側にも途切れずに続きます
- 内側に 4px 浮かせる形（`addonShape="floating"`）も選べます。角は本体と同心の 6px です。欄の外形を入力欄だけのときと同じにしたいときや、グレーを軽く見せたいときに使います
- 塊と入力側の間に、区切りは入れません
- エラーのときは、塊の塗りを赤み（`--color-field-addon-invalid`、`#F1E0DE`）にします。文字の色は変えません。グレーのままだと、赤くなった欄の中で塊だけがエラーから浮いて見えるためです
- suffix に入れるボタンは、パスワードの表示・非表示のように、入力欄そのものを操作するものに限ります。検索のように入力した内容を送るボタンは、入力欄の外に、色のボタンか枠線のボタンとして置きます。グレーのボタンにすると、グレーの入力欄と見分けがつかないためです（[ADR-0024](./adr/0024-neutral-button.md) を見直し）

ユーザーのメモは「そもそも検索だったら外に出すかなと思いました」と「デフォルトでは A のパターンで、B のパターンも選べる、にしたいです。」でした。

**suffix のボタンにキーボードでフォーカスしているあいだは、欄の青い枠線を消し、ボタンのフォーカスの線（[ADR-0031](./adr/0031-focus-visible.md)）だけにします。** 端に接する形・内側に浮かせる形のどちらも同じです。【決定】（[ADR-0040](./adr/0040-field-addon-rest.md)）

- 原則2（フォーカスは欄の枠線で表す）の例外です。いまいる場所を示す線を1本にします。以前は欄の枠線とボタンの線が両方出て、線が2重になり、太く見えていました
- エラーの赤い枠線は消しません。赤い枠線はフォーカスではなく欄の状態なので、赤い枠線とボタンの青い線が両方出ます
- 入力欄にフォーカスしたときと、マウスでボタンを押したときは、今と同じ欄の青い枠線だけです
- 線をグレーの塊の内側に描く案、欄の枠線で塊を囲む案、ボタンを青く塗る案も比べましたが、採りませんでした

**文字の prefix・suffix（「https://」「円」など）は、入力欄の説明（`aria-describedby`）につなぎ、見えている文字は読み上げから外します（`aria-hidden`）。** 名前はラベルのままで、https:// は説明の中で1回だけ読まれます。【決定】（[ADR-0040](./adr/0040-field-addon-rest.md)）

- 説明は、prefix・suffix の文字が先で、キャプション、エラー・警告の文の順に続きます（[原則4](#4-すべての要素はラベル--本体--キャプションの3層)、[ADR-0041](./adr/0041-caption-and-message.md)）。`<TextField label="サイトの URL" prefix="https://" caption="プロフィールに表示します" />` の名前は「サイトの URL」、説明は「https:// プロフィールに表示します」になります
- 文字の suffix も同じです。`<TextField label="月の予算" suffix="円" caption="税込みで入れてください" />` の名前は「月の予算」、説明は「円 税込みで入れてください」で、単独の「円」は読み上げに残りません。prefix と suffix が両方あるときの説明は、prefix → suffix → キャプション → エラーの文の順です。キャプションが本体の上にある既定（F）では、見た目の順（キャプション → prefix → 値 → suffix → エラーの文）と、キャプションの場所だけが違います
- ボタン（`FieldAddonButton`）はつなぎません。ボタンにはフォーカスが止まり、自分の名前で読まれるためです
- Select は変えません。prefix（東京都）は、いまも値の一部として「東京都 足立区」と読まれます
- `FieldAddon` に `aria-hidden` を渡したときは、つなぎません。ラベルに同じことを書くなど、読み上げを呼び出し側で決めるときのためです
- 名前を「ラベル＋prefix」にする案と、prefix と同じことをラベルに書く案（画面に出ない文・見える文）も比べましたが、採りませんでした。どのやり方を採るかは、ライブラリによってまちまちです

ユーザーのメモは「suffix のボタンのフォーカスは、A でよさそうです。」と「一旦 A で行きましょう。」でした。読み上げのやり方は「一旦」なので、使ってみて違和感があれば見直します。文字の suffix は、後から来た「prefix は測ってください。」（prefix と同じ仕組みでつないだ suffix の文字のこと）を受けて、Chrome で測りました（[ADR-0040](./adr/0040-field-addon-rest.md)）。

## 9. 遊びはレイアウト層に置く

巨大な背景文字、隅のキャラクター、見出しの絵文字といった装飾は、**コンポーネントの外側**に置きます。コンポーネント本体は常に真面目なままにしてください。【固定】

装飾をコンポーネントの内部に取り込まないこと。これがシステムの再利用性を守ります。

## 11. 密度は入力方式、構造は画面幅で切り替える

「デスクトップ／モバイル」を1つの判定にせず、原因ごとに分けて切り替えます（[ADR-0004](./adr/0004-density-and-structure-switching.md)）。【固定】ただし、構造を画面幅だけで判定することは、Select について見直しました（下の「見直し」、[ADR-0037](./adr/0037-select-sheet.md)）。

| 何を変えるか                                 | 何で判定するか                            | 理由                                                                      |
| -------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------- |
| 寸法（コントロールの高さ、余白、文字サイズ） | 入力方式（`pointer: coarse` / `fine`）    | 指は精度が低いので大きくする                                              |
| 構造（ポップオーバーかボトムシートか）       | 画面幅。Select は、入力方式と画面幅の両方 | 狭い画面ではポップオーバーが窮屈になる。Select では、指の動きを減らすため |

- 構造を変えてよいのは、ポインタ前提の**浮かぶ UI** に限ります: Select、Menu、Dialog、Tooltip、Popover。それ以外の部品は、寸法だけを変えます
- どちらの判定も、アプリ側から Provider で固定できるようにします。Provider はまだ作っていません。いまは、寸法は `data-density` を付けた要素の中で固定でき、Select の構造は部品ごとの `presentation` で固定します（[ADR-0037](./adr/0037-select-sheet.md)）。指用の高さは、`coarse-large` のクラスで大きくできます（[ADR-0045](./adr/0045-coarse-size.md)）
- マウス用の高さは 40px、文字は 14px です（`--size-control-fine`、`--text-control-fine`）。【決定】（[ADR-0020](./adr/0020-control-size-fine.md)）ユーザーの「パソコン版の入力欄とかの高さがちょっと低すぎるかも」を受けて、仮の値 36px から上げました
- 指用の高さは 44px、文字は 16px です（`--size-control-coarse`、`--text-control-coarse`）。【決定】（[ADR-0045](./adr/0045-coarse-size.md)）要素に `coarse-large` のクラスを付けると、その中の指用の高さが 52px（`--size-control-coarse-large`）になります。アプリ全体では `html` に付けます。マウス用は変わりません。ユーザーのメモは「指用は 44px だなあと思いました。」と「全体テーマ設定のような形で、class を付けることで変化する、とかだとありがたいなと思います。」でした
  - 変わるのは、`--size-control` を読むものの高さです（ボタン・入力欄・Select の本体と選択肢の行・シートの見出しと ×・枠線のリンク・トグルの行）。トグルのトラックとノブも、高さに比例して大きくなります（48×28px・ノブ 22px から 56×32px・ノブ 26px。`--switch-*-coarse-large`）。文字・行の高さ・左右の余白・並べる間・文字のリンクは変わりません。タグは押すものではないので、文字の大きさに従い、変わりません。ユーザーのメモは「52px のときは、トグルは比例して大きくなるようにしたいですね。タグはインタラクティブな要素ではないので、あくまでも文字サイズ依存になりそうです。」と、後から確かめた「トグルの大きさは今で OK です」でした
  - クラスの名前は、いまは `coarse-large` のままです。ユーザーのメモは「クラス名は必要になったら変えましょう。」でした
  - 途中の要素に付けても効くように、密度の規則が `--density-coarse`（指用 1・マウス用 0）を持ち、クラスを付けた要素で `--size-control` とトグルの寸法を計算し直します。`data-density="fine"` の要素の中は 40px のままです

**見直し: Select の構造は、入力方式と画面幅の両方で切り替えます。** 指で操作していて（`pointer: coarse`）、画面が狭いとき（縦長なら 768px（`md`）未満、横長なら 1024px（`lg`）未満）は、選択肢を画面の下から出すシートにします。タブレットとマウスでは、浮かぶ選択肢のままです。【決定】（[ADR-0037](./adr/0037-select-sheet.md)）

- シートにする理由は、画面の狭さではなく、指の動きを減らすことです。そのため入力方式で判定し、そのうえで広い画面（タブレット）は浮かべたままにします
- 部品ごとに `presentation` で出し方を選べます。`"auto"`（既定。上の基準で切り替える）・`"popover"`（いつも浮かべる）・`"sheet"`（いつもシート）です
- シートの見出しは、ラベル → ヘルプテキスト → 欄のエラー・警告です。浮かぶ選択肢には欄の文を出しません。選択肢には、選べない理由や警告の2行目が付くことがあります（[原則4](#4-すべての要素はラベル--本体--キャプションの3層)、[ADR-0044](./adr/0044-message-announce.md)）。項目の高さがそろわないので、シートの半分の高さと浮かぶ選択肢の上限は、項目ごとの高さで数えます
- Menu・Dialog・Tooltip・Popover の構造を何で判定するかは、それぞれを作るときに決めます

最初は、上の表のとおり画面の幅（640px（`sm`）未満）で切り替えていました。ユーザーのメモは「シートを使う利点は、ユーザーの指の動きを緩和するためだと思っています。そうなると、幅が基準にはならないかもしれません。」と、境目についての「幅は横長なら lg にしたいですが、縦長 なら md ですかね」でした。

## 12. 色は面用と前景用の2段で持つ

色のコントラストは、候補を生成するときの制約にします（[ADR-0002](./adr/0002-contrast-and-foreground-tokens.md)）。【固定】

| 対象                                                     | 必要なコントラスト比 |
| -------------------------------------------------------- | -------------------- |
| 本文、ボタンの文字、キャプション                         | 4.5:1                |
| 大きい文字、アイコン、入力欄の枠線、トグル ON などの部品 | 3:1                  |

テイストを保ったまま基準を満たすため、各色を2段で持ちます。

- **面用**: 元の値。塗り、ロゴ、装飾に使います
- **前景用**: 色相と彩度を保ち、明度だけを基準を満たす最小限まで下げた値。文字と枠線に使います

白い文字を載せる面は、前景用の値を使うか、文字を濃紺グレーにします。

例えば警告の黄色（`#EFF16B`）は、白文字で 1.20:1 しかありません。塗りの上の文字は濃紺（`--color-on-warning`）にし、白地の文字には前景用のオリーブ色（`--color-fg-warning`、`#727200`）を使います（[原則6](#6-水色はブランド青は-primaryピンクは-secondary)の「Warning」、[ADR-0038](./adr/0038-warning.md)）。

**例外: スイッチ OFF のトラックには輪郭を付けません**（[ADR-0011](./adr/0011-switch-off-track.md)）。ラウンド2で 3:1 の輪郭を足しましたが、ユーザーの判断で撤回しました。OFF のトラックは、グレーのボタンの塗りと同じ `--color-switch-off`（`#EFF0F1`）で、白地との比は 1.14:1 です（[ADR-0029](./adr/0029-disabled-refine.md)）。3:1 を満たさず、状態はノブの位置と影で伝えます。OFF と Disabled の区別は、Disabled の側の見た目で付けます。押せない OFF のトラックは明るいグレー（`--color-switch-off-disabled`、`#E1E3E4`）で、ノブの影がなくなります（[原則1](#1-影は押せることの記号)）。後半の軸 11 では、OFF のトラックにほんのり枠（1px）を付ける案も比べましたが、採りませんでした（[ADR-0029](./adr/0029-disabled-refine.md)）。

なお、ラウンド1でスイッチが ON に見えなかったのは、キャンバス側の描画の不具合です。デザインの決定ではありません。

ARIA などのアクセシビリティ対応は、README のとおり後回しにします。先に扱うのは、見た目に焼き込まれるものだけです。トークンの値に焼き込まれる色のコントラストと、キーボードで操作したときのフォーカスの見た目（[原則2](#2-状態は枠線で表す)、[ADR-0031](./adr/0031-focus-visible.md)）です。例外として、入力欄の文字の prefix・suffix の読み上げ（[原則8](#8-入力欄の様式は編集できるかで決まる)、[ADR-0040](./adr/0040-field-addon-rest.md)）と、キャプションとエラー・警告の読み上げの順（[原則4](#4-すべての要素はラベル--本体--キャプションの3層)、[ADR-0041](./adr/0041-caption-and-message.md)）、入力欄と Select の待っているあいだの `aria-busy`・`aria-disabled` と読み込み中の行の `role="status"`（[原則1](#1-影は押せることの記号)、[ADR-0042](./adr/0042-field-loading.md)）、お知らせの `role="alert"`・`role="status"`（[原則6](#状態の色とお知らせ)、[ADR-0043](./adr/0043-notice.md)）、エラー・警告の行の `aria-live="polite"` と、送信したときのフォーカス（一覧は `role="group"`）（[原則4](#4-すべての要素はラベル--本体--キャプションの3層)、[ADR-0044](./adr/0044-message-announce.md)）は、見た目の比較と一緒に決めました。

## 後半の軸（Storybook で1軸ずつ詰める）

- 指用の高さの残り（原則11）: 高さは [ADR-0045](./adr/0045-coarse-size.md) で決まった（44px。`coarse-large` のクラスを付けた要素の中は 52px）。次のことは、どうするかを決めていない
  - 大きい指用で、文字・左右の余白・並べる間を変えるか。比べていない（いまは高さだけが変わる）
  - どんな場面で大きい指用を使うか
  - Select の選択肢は `body` の直下に出るので、途中の要素にクラスを付けたときは、`container` をその中にしないと選択肢の行が 44px のまま（CSS から読み取ったことで、測っていない）
  - 寸法を Provider で固定する仕組みがまだない。クラスは `html` か要素に直接付ける
- Warning の残り（原則6）: 色の役割は [ADR-0038](./adr/0038-warning.md)、お知らせは [ADR-0043](./adr/0043-notice.md) で決まった。次のことは、まだ作っていない
  - 警告の色のボタンは、必要になったら Button の `color` に足す
- お知らせと状態の色の残り（原則6）: 状態の色とお知らせの見た目は [ADR-0043](./adr/0043-notice.md) で決まった。次のことは、まだ作っていないか、決めていない
  - 入力欄の下の成功・情報の行（[ADR-0041](./adr/0041-caption-and-message.md) の形）は作っていない。白地の文字の役割（`--color-fg-success`・`--color-fg-info`）はある
  - 部品は、role の箱と中身を一緒に出す。あとから出すお知らせを多くの読み上げソフトで知らせるには、箱を先に置いておき中身だけを入れる必要がある。その仕組み（空の箱を置いておく部品など）はまだない
  - 黄色の塗り（`filled` の警告）は白地との比が 1.20:1 だが、影を付けないので縁もない。淡い面と同じく、面の色だけで置いている
  - 操作の場所には、白いボタンと文字のリンクを置く前提。枠線のリンクなど、ほかの部品は確かめていない
  - × の読み上げの名前は「閉じる」で固定

# 実装方針

- **React**
- **ヘッドレス UI ライブラリ**を挟む。Base UI（`@base-ui/react`）を使う。後半の最初の部品 Select から使い始めた
- Button / Input / Textarea / Card / Badge は素の要素で実装する。ライブラリを挟まない
- ヘッドレスが必要なのは Select / Dialog / Tooltip / Popover / Tabs から

```
src/
  tokens/      色・余白・角丸・影・タイポ
  primitives/  ヘッドレスをラップした内部層
  components/  公開するのはここだけ
```

**最初に作るコンポーネント: Select**

理由は、ネイティブ `<select>` では表現できない最初のコンポーネントであり、同時に原則1〜3・7・8がすべて同時に検証できるためです（塗り／枠線／エラーの3状態、prefix 付き、影と hover の挙動）。原則11で構造を切り替える対象（浮かぶ UI）でもあるため、ポップオーバーとボトムシートの切り替えも最初に検証できます。

## 和文の縦位置

入力欄の和文が上に寄る問題は、和文フォント（IBM Plex Sans JP）の縦の寸法を補正して直しました。【決定】（[ADR-0032](./adr/0032-text-offset.md)）

ラウンド2でユーザーから質問がありました。「お名前の入力欄に入っている文字が上によって見えるのは錯覚やレンダリングの問題ですか？」

錯覚ではなく、補正する前は実際に約 1px 上に寄っていました。高さ 44px の入力欄で、文字のインクの上下の余白を画素で測った結果は次のとおりです（差＝下の余白 − 上の余白。正の値ほど上に寄っている）。

| 要素  | フォント指定 | 文字列         | 上の余白 | 下の余白 | 差      |
| ----- | ------------ | -------------- | -------- | -------- | ------- |
| input | Mulish＋和文 | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| div   | Mulish＋和文 | 山田 花子      | 12.75px  | 12.75px  | 0.00px  |
| input | 和文のみ     | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| div   | 和文のみ     | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| input | どちらも同じ | お仕事のご相談 | —        | —        | +2.25px |
| input | どちらも同じ | 国国国国       | —        | —        | +1.50px |

- IBM Plex Sans JP の和文は、和文フォントだけで組むと約 1px 上に寄っていました（差 1.5〜2.25px）
- 英字フォント（Mulish）を先頭に置いた div では、中央に来ていました
- input では、フォント指定にかかわらず、和文フォントだけのときと同じく上に寄っていました。そのため、TextField の値（input）と Select の値（div）で、縦位置が約 1px ずれていました

### 原因と補正

原因は、和文フォントの、行の位置を決める寸法（hhea: 上 1.06em・下 0.44em）です。この中心は、漢字の枠（上 0.88em・下 0.12em。フォントの typo の寸法）の中心より 0.07em 低く、16px では約 1.1px です。

- 和文フォントが行の位置を決めると、漢字が上に寄ります。input では、実際に文字を描くフォントが行の位置を決めるため、値が和文だけのときに上に寄っていました
- Select の値（div）やボタンでは、先頭の英字フォント（Mulish）が行の位置を決めます。Mulish の行の中心は漢字の枠の中心とほぼ同じなので、和文は中央に来ていました

補正は次のとおりです。【決定】（[ADR-0032](./adr/0032-text-offset.md)）

- IBM Plex Sans JP の `@font-face` に、`ascent-override: 88%`、`descent-override: 12%`、`line-gap-override: 0%` を足します。縦の寸法を漢字の枠に合わせるので、和文がどこでも行の中央に来ます。英字フォント（Mulish）は元のままです
- `@fontsource/ibm-plex-sans-jp` の CSS は書き換えられません。そのため、補正を足した `@font-face` を `scripts/generate-fonts.mjs`（`pnpm run fonts`）で `src/styles/ibm-plex-sans-jp.css` に書き出し、`src/styles/globals.css` から読みます。このファイルは手で書き換えません
- `@fontsource/ibm-plex-sans-jp` を更新したら、`pnpm run fonts` を流し直し、`node design/tools/measure-text-offset.mjs` で測って確かめます

補正したあとに、同じ道具で測った結果です（16px、高さ 44px の入力欄）。

| 要素       | フォント指定 | 文字列             | 差      |
| ---------- | ------------ | ------------------ | ------- |
| input      | Mulish＋和文 | 山田 花子          | 0.00px  |
| div        | Mulish＋和文 | 山田 花子          | 0.00px  |
| input      | 和文のみ     | 山田 花子          | 0.00px  |
| div        | 和文のみ     | 山田 花子          | 0.00px  |
| input・div | Mulish＋和文 | お仕事のご相談     | +0.25px |
| input・div | Mulish＋和文 | hanako@example.com | −3.75px |

- 和文は、input でも div でも中央に来ます。TextField の値と Select の値の縦位置もそろいました
- 小文字の英字（メールアドレス）は下に寄って見えます。小文字は大文字より背が低く、下に伸びる文字もあるためです。英字の組版では普通の見え方なので、補正しません

### 行の高さの端数による 1px のずれ（対応済み）

後半の軸 07 で、ユーザーから次の指摘がありました。「何か下の方に行くにつれてボタンの文字が上にずれてます…？」

これは和文の縦位置とは別の原因です。高さ 40px のボタンに行の高さ 21px（14px × 1.5）の文字を中央に置くと、上下の余白が 9.5px の端数になります。ブラウザは、部品の輪郭と文字をそれぞれ画素に丸めて描きます。そのため、部品が置かれた位置（y 座標の端数）によって、文字だけが 1px 上下にずれます。

- **行の高さは整数 px にし、部品の高さとの差を偶数にします。** 上下の余白が整数になり、どこに置いても文字と輪郭が同じように丸められます（`--leading-control`: マウス用 20px・指用 24px、`--leading-label`: 20px、`--leading-caption`: 16px）
- 部品の外側（ページのレイアウト）の端数は、部品の側では防げません。部品の中の余白を整数にしておけば、ずれは出ません
