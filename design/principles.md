# デザイン原則

このドキュメントは、コンポーネントを生成・実装する際の判断基準です。
個別の実装で迷ったときは、トークンの値ではなく**ここに書かれた「なぜ」に立ち返って**判断してください。

値は [`tokens.css`](./tokens.css) に、決定の経緯は [`adr/`](./adr/) にあります。ブラッシュアップの進め方は [`README.md`](./README.md) を参照してください。

前半（ムード探索）は終わりました。前半の決定をすべて反映した見た目は、[`rounds/p1-final/`](./rounds/p1-final/)（design キャンバスの最終版）で確認できます。

## 各項目の印

原則はまだブラッシュアップの途中です。各項目に次の印を付けています。

| 印           | 意味                                             |
| ------------ | ------------------------------------------------ |
| 【固定】     | 参照画像と原則が一致しており、ループでは振らない |
| 【決定】     | ループで決まった。根拠の ADR を併記する          |
| 【前半の軸】 | 前半（design キャンバス）でムードとして振る      |
| 【後半の軸】 | 後半（Storybook）で1軸ずつ詰める                 |

画像と原則が食い違っている箇所は、どちらも仮説として扱い、ループで決めます（[ADR-0001](./adr/0001-judgement-criteria.md)）。【固定】の項目でも、ループ中にユーザーが違和感を示した場合は軸に戻します。

# 存在理由

**デスクトップでもモバイルでも、それぞれに適した密度にすること。**

デスクトップ優先の UI はモバイルに合わず、モバイル優先の UI はデスクトップで密度が低くなります。このアンバランスを解消することが、このシステムを作る動機です（[原則11](#11-密度は入力方式構造は画面幅で切り替える)）。

# 判断の基準

候補を選ぶとき、また実装で迷ったときは、次の4語に最も近いものを選びます（[ADR-0001](./adr/0001-judgement-criteria.md)）。

| 基準の言葉     | 画面上で見るところ                                   |
| -------------- | ---------------------------------------------------- |
| **軽い**       | 影は弱く、線は細く、余白は多い                       |
| **やわらかい** | 角が丸い。文字は黒ではなく濃紺グレー（`--color-fg`） |
| **整然**       | 部品の構造が揃っている（3層構成、状態の規則）        |
| **人懐っこい** | 水色・ピンク・pill・和欧併記                         |

## 顔: 構造は実直、個性はトークン層

- **構造**（状態の表し方、影、塗りと枠線）は実直にします。参照画像のうち、コンポーネント見本の側に寄せます
- **個性**（色、角丸、文字、和欧併記）はトークン層に出します。参照画像のうち、Web サイトの側に寄せます

「整然」は構造が、「人懐っこい」はトークンが担います。

## ポップさの出し方: トークン層＋動き

温かみとポップさは、トークン層と動きで出します。動きは[原則3](#3-hover-は一段沈む)「一段沈む」の延長として、押下時にバネのように沈む、といった形にします。

コンポーネントの内部に装飾を持ち込むことはしません（[原則9](#9-遊びはレイアウト層に置く)）。

## 反例

次のような見た目は、基準から外れています。ループで却下した候補から、ここに追加していきます。

- マテリアルデザインのような、影で階層を作る硬い見た目
- 字間を大きく空けた英字ラベル。AI が作ったように見えます（[ADR-0010](./adr/0010-section-label.md)）

# 原則

## 1. 影は「押せること」の記号

影は**塗りのあるボタンにのみ**付けます。それ以外（カード、フォーム部品、枠線のみのボタン）には付けません。【固定】

この規則により、構造だけで3つの状態が区別できます。

| 見た目                | 意味                 |
| --------------------- | -------------------- |
| 塗りがある + 影がある | 押せる               |
| 枠線のみ + 影なし     | 押せるが主役ではない |
| 塗りがある + 影がない | 押せない（Disabled） |

**Disabled は色を薄くする必要がありません。** 影がないこと自体が「押せない」の表現です。色による表現は補助として使い、主たる表現にはしないでください。【後半の軸】

> **後半の軸: Disabled の表し方。** 参照画像（`references/component-buttons.webp`）の Disabled は、濃いグレーの塗りに薄い文字で、色を変えています。この段落の「色を薄くしない」と逆です。
>
> ユーザーの方向性: **Disabled は見た目を変える**（スイッチ OFF と区別できるように）。「スイッチ OFF の輪郭はいらないかも。前と同じでよいです。disabled の時の見た目を変える方がよさそう。」（[ADR-0011](./adr/0011-switch-off-track.md)）。この方向性も、この段落の「色を薄くする必要がありません」とは逆です。
>
> **後半の軸: 原則2との矛盾。** 上の表では「塗りがある + 影がない」が Disabled です。一方、原則2の入力欄の通常状態は「グレー塗り・枠線なし」で影もないため、この表に当てはめると「押せない」と読めてしまいます。

階層や奥行きは、影ではなく**面の明度差と余白**で作ります。カードが浮いて見えるのは影のためではなく、背景より明るい面だからです。【固定】

影の値は、輪郭程度のごく薄い影に決まりました。hover では輪郭だけが残り、押下で消えます（`--shadow-raised`、`--shadow-raised-hover`）。【決定】（[ADR-0006](./adr/0006-button-shadow.md)）

## 2. 状態は「塗り ⇄ 枠線」の入れ替えで表す

このシステムで最も特徴的な規則です。一般的な「濃くする／薄くする」方式は使いません。

フォーム部品の場合:

| 状態       | 表現                                    | 印           |
| ---------- | --------------------------------------- | ------------ |
| 通常       | グレー塗り（`--color-field`）・枠線なし | 【固定】     |
| フォーカス | 白塗り + 青の枠線（`--color-primary`）  | 【後半の軸】 |
| エラー     | 白塗り + 赤の枠線（`--color-danger`）   | 【後半の軸】 |

> **後半の軸: フォーカス時の変化量。** ラウンド1でユーザーから次の指摘がありました。「全体を通して、入力欄をクリックしたときにグレー背景から一気に白になってフォーカスリングが付くのはちょっとアニメーションとして大きすぎる気もします。」フォーカスの表現は参照画像と一致していたため【固定】としていましたが、ユーザーの判断を優先して軸に戻しました。塗りと枠線を同時に切り替えるか、どちらか一方にするか、変化をどう段階づけるかを後半で詰めます。
>
> **後半の軸: エラー時の塗り。** 参照画像（`references/component-text-fields.webp`、`references/component-selects.webp`）のエラー状態は、グレー塗りのまま赤枠になっているように見えます。上の表の「白塗り」と違います。

面と線が入れ替わることで状態が変わります。明度を変えて状態を表すことは**しないでください**。

> **後半の軸: 原則3との矛盾。** 原則3では、平らな要素の hover を「背景が1段濃くなる」としています。これは明度で状態を表しており、この段落と衝突します。

## 3. hover は「一段沈む」

すべてのインタラクティブ要素に共通する上位規則です。要素の種類によって表れ方が変わります。【固定】

| 要素         | hover                         | 押下                      |
| ------------ | ----------------------------- | ------------------------- |
| 影のある要素 | 影が減る                      | 影が消える（接地）        |
| 平らな要素   | 背景が1段濃くなる【後半の軸】 | さらに1段濃く【後半の軸】 |

影を完全に消すのは押下に取っておいてください。hover で消してしまうと、押下との区別がつきません。【固定】

**hover に枠線を使ってはいけません。** 枠線は原則2でフォーカスに割り当てられており、役割が衝突します。【固定】

**タッチ環境では hover が存在しません。** 指で操作するときは、押下時の変化を hover 以上にはっきり付けてください。【固定】

押下の動きは、100ms で素早く 1px 沈み、弾ませません（`--duration-press`、`--ease-press`、`--press-depth`）。【決定】（[ADR-0009](./adr/0009-press-motion.md)）影の値は [ADR-0006](./adr/0006-button-shadow.md) で決まっています。

---

## 4. すべての要素は「ラベル / 本体 / キャプション」の3層

ボタンにもキャプションが付きます。これは例外ではなく既定です。【固定】

- ラベル: 太字、本体の上
- 本体: コンポーネント
- キャプション: 小さくグレー（`--color-fg-subtle`）、本体の下

キャプションは省略可能ですが、**省略された場合でもレイアウトが崩れない**ように実装してください。

## 5. 角丸は部品と包むもので分ける

| 対象                                   | 角丸                              | トークン              | 印                                                      |
| -------------------------------------- | --------------------------------- | --------------------- | ------------------------------------------------------- |
| ボタン・入力欄（フォーム部品）         | 12px で統一。密度によって変えない | `--radius-control`    | 【決定】（[ADR-0008](./adr/0008-control-radius.md)）    |
| カード（標準・入れ子の型とも）         | 16px                              | `--radius-card`       | 【決定】（[ADR-0016](./adr/0016-card-radius.md)）       |
| 入れ子の型のカードの余白（画像の周り） | 8px。画像の角丸は同心で 8px       | `--card-nested-inset` | 【決定】（[ADR-0014](./adr/0014-nested-card-inset.md)） |
| カードの画像の比率                     | 16:9                              | `--card-media-aspect` | 【決定】（[ADR-0017](./adr/0017-card-media-aspect.md)） |
| リンク・タグ・トグルなどの小物         | 完全な pill                       | `--radius-pill`       | 【固定】                                                |

ボタンと入力欄は同じ値に揃えます。角丸を高さに比例させる規則は採りません。密度を切り替えると見た目が変わり、揃えたいときに困るためです（「B のように比例する形式だと、ルックが揃えたくても見た目が変わって困ることありそう。」）。

カードは2つの型に分けます。ラウンド2のユーザーのメモ「カードについては入れ子のタイプだとちょっと過剰カモ。このタイプも選べるようにするのであれば、下の角丸が丸すぎる気持ち。」を受けたものです。

- **標準のカード**: 画像を端まで届かせる
- **入れ子の型**: 画像を内側に角丸で収める型。利用者が選べる型として用意する。画像の角丸は、外側の角丸 − 余白（同心）

標準のカードと入れ子の型は、同じ角丸 16px を使います。ラウンド4のユーザーのメモ「角丸を通常版と入れ子版で変えるのはちょっとうーんという感じもしますが、画像の角丸に影響してくるので、入れ子の方が控えめの方がいいかもですね。」を受けて比べた結果、入れ子も 16（画像は 8）に決まりました（[ADR-0016](./adr/0016-card-radius.md)）。画像の比率は、どちらの型も 16:9 です（[ADR-0017](./adr/0017-card-media-aspect.md)）。

## 6. 水色はブランド、青は Primary、ピンクは Secondary

水色は構造の色で、見出しとロゴに使います。青（Primary）とピンク（Secondary）は、色を持つ部品（ボタン、スイッチ、タグ、リンクなど）で**利用者が選ぶ色**です。

| 色     | 役割             | 面用（塗り・装飾）  | 前景用（文字・枠線・白文字を載せる塗り） | 使いどころ                     | 印                                                    |
| ------ | ---------------- | ------------------- | ---------------------------------------- | ------------------------------ | ----------------------------------------------------- |
| 水色   | ブランド（構造） | `--color-brand`     | `--color-fg-brand`                       | ロゴ、見出し、セクションラベル | 【固定】                                              |
| 濃い青 | Primary          | `--color-primary`   | `--color-primary`                        | 利用者が選ぶ。フォーカス枠     | 【決定】（[ADR-0012](./adr/0012-primary-blue.md)）    |
| ピンク | Secondary        | `--color-secondary` | `--color-fg-secondary`                   | 利用者が選ぶ。用途を限定しない | 【決定】（[ADR-0013](./adr/0013-secondary-color.md)） |

- **Primary と Secondary に用途の区別はありません。** その場所に最も合う色を、コンポーネントの利用者が選びます（「ピンクの使いどころは、単に Secondary という立ち位置なので、限定されません。その場所に最も合う色をコンポーネントの利用者が選ぶことになります。」）。以前の「青が『進む』、ピンクが『寄り道』」「ピンクを主要アクションに使わない」は廃止しました
- **Primary の青は `#2474DF`** です。一旦この値で確定しており、後で見直してかまいません（「Primary は一旦これで。」）。白地で 4.53:1 あるため、面用と前景用は同じ値です
- **Secondary の塗りに白文字を載せるときは、前景用の `--color-fg-secondary`（`#E41966`、白文字で 4.54:1）を使います。** 面用の `--color-secondary`（`#F53273`）は白文字で 3.76:1 しかないため、文字を載せない塗り（トグル ON など）に使います（[原則12](#12-色は面用と前景用の2段で持つ)）
- 各部品で、利用者が指定しないときにどちらの色になるか（既定の色）は【後半の軸】です

水色の面に載せる文字は `--color-on-brand`（濃紺グレー）です。水色の前景用 `--color-fg-brand` は白地で 3.02:1 なので、大きい文字（見出し、セクションラベル）にしか使えません。

タグは、淡い水色の面（`--color-tag`）に同じ色相の濃い水色の文字（`--color-on-tag`）を載せます。【決定】（[ADR-0007](./adr/0007-tag-color.md)）

### Danger と Secondary の区別【後半の軸】

[ADR-0013](./adr/0013-secondary-color.md) でピンクの用途を限定しなくなったため、ピンクの塗りのボタンが削除ボタン（Danger）の隣に並ぶ場面がありえます。この軸の優先度は上がりました。

Danger は、旧値 `#EE4665` から `#D4283F` に変更されています。変更の理由は「旧値は Secondary `#F53273` と明度が近く、削除ボタンと More ボタンが隣り合うと区別できなかった。明度差をつけることで、色相に頼らずに区別できる」というものでした。

ただし、実測した明度差は小さく、この根拠は弱いです。

| 組み合わせ                                    | コントラスト比 |
| --------------------------------------------- | -------------- |
| ピンク（面用）`#F53273` と Danger `#D4283F`   | 1.34:1         |
| ピンク（前景用）`#E41966` と Danger `#D4283F` | 1.11:1         |

前景用のピンクは明度を下げているため、Danger との差はさらに小さくなっています。区別の手段（明度、色相、形、アイコンなど）は後半で決めます。

ユーザーの方向性: Danger はもう少し濃くしてよい（「Danger はもうちょっと濃くしてもいいかも。」）。

## 7. 塗りか枠線かの使い分け

- **既定**: 画面内で最も進めたい操作は塗り、それ以外は枠線【固定】
- **例外**: 密度の高い並び（カード内リンク、SNS アカウント一覧など）では、塗りが重すぎるため枠線に落とす【固定】

## 8. 入力欄の様式は「編集できるか」で決まる

| 用途                     | 様式                          |
| ------------------------ | ----------------------------- |
| 編集できる（フォーム）   | グレー塗り（`--color-field`） |
| 読み取り専用（情報表示） | 下線のみ（`--color-line`）    |

ユーザーから見ると「**下線が出てきたら読むだけ**」という判別規則になります。この対応を崩さないでください。【固定】

## 9. 遊びはレイアウト層に置く

巨大な背景文字、隅のキャラクター、見出しの絵文字といった装飾は、**コンポーネントの外側**に置きます。コンポーネント本体は常に真面目なままにしてください。【固定】

装飾をコンポーネントの内部に取り込まないこと。これがシステムの再利用性を守ります。

---

## 10. 和欧併記

日本語見出し + 英語サブ、が基本単位です。【固定】

英語のセクションラベルは、すべて大文字・太字（800）・20px・字間 0.04em・前景用の水色です（`--label-transform`、`--label-style`、`--label-size`、`--label-weight`、`--label-tracking`）。【決定】（[ADR-0010](./adr/0010-section-label.md)）

参照画像では、大文字（WORKS）、先頭だけ大文字（Biography）、イタリック（_My Value_）と揺れていましたが、大文字に揃えます。字間は空けすぎないでください（反例）。

## 11. 密度は入力方式、構造は画面幅で切り替える

「デスクトップ／モバイル」を1つの判定にせず、原因ごとに分けて切り替えます（[ADR-0004](./adr/0004-density-and-structure-switching.md)）。【固定】

| 何を変えるか                                 | 何で判定するか                         | 理由                                   |
| -------------------------------------------- | -------------------------------------- | -------------------------------------- |
| 寸法（コントロールの高さ、余白、文字サイズ） | 入力方式（`pointer: coarse` / `fine`） | 指は精度が低いので大きくする           |
| 構造（ポップオーバーかボトムシートか）       | 画面幅                                 | 狭い画面ではポップオーバーが窮屈になる |

- 構造を変えてよいのは、ポインタ前提の**浮かぶ UI** に限ります: Select、Menu、Dialog、Tooltip、Popover。それ以外の部品は、寸法だけを変えます
- どちらの判定も、アプリ側から Provider で固定できるようにします
- 指用とマウス用の寸法の差は、仮の値（`--size-control-coarse: 44px`、`--size-control-fine: 36px`）です。差の詰めは【後半の軸】です

## 12. 色は面用と前景用の2段で持つ

色のコントラストは、候補を生成するときの制約にします（[ADR-0002](./adr/0002-contrast-and-foreground-tokens.md)）。【固定】

| 対象                                                     | 必要なコントラスト比 |
| -------------------------------------------------------- | -------------------- |
| 本文、ボタンの文字、キャプション                         | 4.5:1                |
| 大きい文字、アイコン、入力欄の枠線、トグル ON などの部品 | 3:1                  |

テイストを保ったまま基準を満たすため、各色を2段で持ちます。

- **面用**: 元の値。塗り、ロゴ、装飾に使います
- **前景用**: 色相と彩度を保ち、明度だけを基準を満たす最小限まで下げた値。文字と枠線に使います

白い文字を載せる面は、前景用の値を使うか、文字を濃紺グレーにします。

**例外: スイッチ OFF のトラックには輪郭を付けません**（[ADR-0011](./adr/0011-switch-off-track.md)）。ラウンド2で 3:1 の輪郭を足しましたが、ユーザーの判断で撤回しました。OFF のトラックは 3:1 を満たさず、状態はノブの位置と影で伝えます。OFF と Disabled の区別は、Disabled の側の見た目で付けます。

なお、ラウンド1でスイッチが ON に見えなかったのは、キャンバス側の描画の不具合です。デザインの決定ではありません。

キーボード操作や ARIA などのアクセシビリティ対応は、README のとおり後回しにします。先に扱うのは、トークンの値に焼き込まれる色のコントラストだけです。

# カラートークン

値は [`tokens.css`](./tokens.css) にだけ書きます。トークンは値の層（`--palette-*`）と役割の層に分かれており、部品と原則は役割の層だけを参照します（[ADR-0003](./adr/0003-token-layers.md)）。

| 分類                | 役割トークン                                                                                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 地と面              | `--color-bg`、`--color-surface`、`--color-field`、`--color-field-addon`、`--color-neutral`、`--color-line`                                                               |
| 文字                | `--color-fg`、`--color-fg-muted`、`--color-fg-subtle`                                                                                                                    |
| ブランド（水色）    | `--color-brand`、`--color-fg-brand`、`--color-on-brand`、`--color-tag`、`--color-on-tag`                                                                                 |
| Primary（濃い青）   | `--color-primary`、`--color-on-primary`                                                                                                                                  |
| Secondary（ピンク） | `--color-secondary`、`--color-fg-secondary`、`--color-on-secondary`（ラウンド3までは `--color-accent` 系の名前でした。[ADR-0013](./adr/0013-secondary-color.md) で改名） |
| 注意                | `--color-danger`、`--color-on-danger`                                                                                                                                    |

地と中立色は、白地と無彩色寄りの中立色（色相 220・彩度 0.002 で明度だけを変える）に決まりました。【決定】（[ADR-0005](./adr/0005-neutral-and-background.md)）

旧トークンからの主な変更:

- キャプション色（旧 Text_Light）は `#788287`（白地 3.93:1）から `#6E787D`（白地 4.52:1）に変更しました
- 旧 `Dark #1F3737` は誤記とみなし、文字色 `#1F2F37` に統一しました。ユーザー確認済みです（「Dark はこれで良さそうです。」）
- 旧 LightGray `#F4F5F5`・Gray `#E2E2E2` は、ADR-0005 の中立色（`--palette-gray-50`〜`300`）に置き換えました
- Success、Warning、Info、LightGreen（`--palette-mint-50`）は、値の層にだけあり、役割はまだ定義していません
- 旧 Danger_Pale は、Danger を濃くしたのに合わせて彩度を上げる必要があり、値が未定です（Warning の扱いと合わせて後半で決めます）

# 実装方針

- **React**
- **ヘッドレス UI ライブラリ**を挟む（Base UI を第一候補として検討中）
- Button / Input / Textarea / Card / Badge は素の要素で実装する。ライブラリを挟まない
- ヘッドレスが必要なのは Select / Dialog / Tooltip / Popover / Tabs から

```
src/
  tokens/      色・余白・角丸・影・タイポ
  primitives/  ヘッドレスをラップした内部層
  components/  公開するのはここだけ
```

**最初に作るコンポーネント: Select**

理由は、ネイティブ `<select>` では表現できない最初のコンポーネントであり、同時に原則1〜3・7・8がすべて同時に検証できるためです（塗り／枠線／エラーの3状態、prefix 付き、影と hover の挙動）。原則11で構造を切り替える対象（浮かぶ UI）でもあるため、ポップオーバーとボトムシートの切り替えも最初に検証できます。

## 和文の縦位置

ラウンド2でユーザーから質問がありました。「お名前の入力欄に入っている文字が上によって見えるのは錯覚やレンダリングの問題ですか？」

錯覚ではなく、実際に約 1px 上に寄っています。高さ 44px の入力欄で、文字のインクの上下の余白を画素で測った結果は次のとおりです（差＝下の余白 − 上の余白。正の値ほど上に寄っている）。

| 要素  | フォント指定 | 文字列         | 上の余白 | 下の余白 | 差      |
| ----- | ------------ | -------------- | -------- | -------- | ------- |
| input | Mulish＋和文 | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| div   | Mulish＋和文 | 山田 花子      | 12.75px  | 12.75px  | 0.00px  |
| input | 和文のみ     | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| div   | 和文のみ     | 山田 花子      | 11.75px  | 13.75px  | +2.00px |
| input | どちらも同じ | お仕事のご相談 | —        | —        | +2.25px |
| input | どちらも同じ | 国国国国       | —        | —        | +1.50px |

- IBM Plex Sans JP の和文は、和文フォントだけで組むと約 1px 上に寄ります（差 1.5〜2.25px）
- 英字フォント（Mulish）を先頭に置いた div では、中央に来ます
- input では、フォント指定にかかわらず、和文フォントだけのときと同じく上に寄ります。そのため、TextField の値（input）と Select の値（div）で、縦位置が約 1px ずれます

対応は実装段階（後半）で行います。`@font-face` の `ascent-override`／`descent-override` などで補正し、`node design/tools/measure-text-offset.mjs` で測って確かめます。
