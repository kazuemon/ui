# 0096. Prose の作り

- ステータス: Accepted
- 日付: 2026-09-17
- ラウンド: 後半（Prose の前提）

## 背景

Prose（記事の本文を包む部品）を作る前に、何を受け取り、どこまでの見た目を持つかを決めます。backlog（`design/backlog.md` の「本文（Prose・CodeBlock など）」）には、2026-09-13 時点の方針として「Prose は、MDX に渡す部品の対応表（`h2` → Heading、`pre` → CodeBlock など）と、要素のあいだの余白を持つ包みにし、見た目は各部品に持たせ、素の要素に CSS を当てる形（Tailwind Typography の `prose`）にはしない」と書かれていました。この方針のまま進めるかを含めて確かめました。

## 候補

比較の候補はありません。前提を尋ねた質問と、それぞれの答えです。

| 質問                                      | 答え                                                                                          |
| ----------------------------------------- | --------------------------------------------------------------------------------------------- |
| Prose が受け取る形                        | 変換済みの HTML だけを想定する（`h1`・`h2`・`p` など）。Markdown からの変換は利用者にゆだねる |
| 引用・コールアウトなどの囲みの記法        | 変換しない                                                                                    |
| 特定の部品（`h2` → Heading など）への変換 | 利用者にゆだねる（ドキュメントで対応表の例を示すことはある）                                  |
| 見た目を変えたいとき                      | Prose の props では選べるようにせず、利用者が部品を直接使う                                   |
| 表の幅                                    | 中身の幅を尊重する                                                                            |
| props                                     | `as` だけ                                                                                     |

## 決定

**Prose は、変換済みの素の HTML（`h1`〜`h6`・`p`・`a`・`strong`・`em`・`del`・`mark`・`code`・`kbd`・`br`・`ul`・`ol`・`li`・チェックリスト・`blockquote`・`pre.shiki`・`table`・`img`・`hr`・GFM の脚注）に、読む部品と同じ見た目を CSS で当てる包みにします。**

- MDX の対応表（`h2` → Heading など）は作りません。特定の部品への変換は利用者にゆだねます
- 引用符・コールアウトのような、Markdown にない記法への変換もしません
- 見た目のクラス列は、部品（Blockquote・Divider・Figure・List・Footnote・Heading・Table・Text・CodeBlock・inline-styles）と同じもの（`src/internal/reading/`）を、根の要素に当てます。根には `data-prose` を付け、根そのものには効かせません
- 文字のリンクは Primary の青にします（記事の中では、押せる文字を本文と見分けやすくするためです）
- JS が要る機能（表の横スクロールの包みに Tab で移る、コードのコピーのボタン）は付きません。表と `pre` は CSS だけで横にスクロールします
- 表の幅は中身の幅を尊重します。幅に満たない表は、部品と違い幅いっぱいには広がりません
- props は `as`（描く要素。`div`・`article`・`section`・`main`）だけです。見た目を変えたいときは、Prose に頼らず部品を直接使う想定です

## 理由

ユーザーのメモです。

> HTML のみ想定すればOKです（h1, h2, p など…）Markdown の変換は利用者にゆだねます

> 変換しない

> 特定コンポーネントへの変換はユーザーに委ねるつもりです（ドキュメントを作るときに一緒に基本だけ作ってもいいかなというくらい）その他は認識通りです。

> 1: Prose を使って見た目を作るのは利用者の責務にします。

> 2: primary にしたいです。

> 3: 1と同じく、Prose のなかで見た目を変えたい場合はコンポーネントを直接使ってもらう想定です。Props はなしでOK

> 4: 中身の幅尊重でOKです

- **HTML だけを想定**: Markdown のパースをライブラリの外に置くという、2026-09-13 の方針（backlog）を踏襲しました。ブログ側（remark/rehype など）のパイプラインに委ね、Prose はその出力の見た目だけを引き受けます
- **素の要素に CSS を当てる形に変更**: backlog に書かれていた「素の要素に CSS を当てる形にはしない」という前提を覆しました。当初は、部品への対応表を持つ包みを考えていましたが、「HTML のみ想定」「特定コンポーネントへの変換はユーザーに委ねる」という答えにより、Prose 自身が対応表を持つ理由がなくなりました。見た目は、部品と全く同じクラス列（`src/internal/reading/`）を素の要素に直接当てることで、記事の外で使う部品と見た目がずれない、という元の目的は保っています
- **props を持たない**: 見た目の選択肢（色・角丸の有無など）を Prose の props として持つと、対応する部品の props と二重になります。見た目を変えたい利用者は、Prose を使わず部品を直接使う、という一本の道にしました

## 却下した案と理由

- MDX の対応表を Prose が持つ案（backlog の当初の方針）: 選ばれませんでした。「HTML のみ想定」「変換はユーザーに委ねる」という答えにより、対応表を持つ理由がなくなりました
- 見た目を props で選べるようにする案: 選ばれませんでした。Prose の外で部品を直接使う形に一本化しました

## 影響

- `src/components/prose/Prose.tsx`: 見た目のクラス列（`src/internal/reading/` の `blocks.ts`・`code.ts`・`code-block.ts`・`footnote.ts`・`heading.ts`・`list.ts`・`table.ts`・`text.ts`・`text-link.ts`）を1つの `className` にまとめ、根に `data-prose`・`data-reading` を付けます。部品と作りが違うところ（`blockquote` を `block` にする、`table` を `overflow-x-auto` にする、Shiki の地を `--shiki-background` から拾う）は `htmlOnly` にまとめています
- `src/internal/reading/`: 2つ以上の場所（各部品と Prose）が使う見た目を持つ、新しいディレクトリです。CLAUDE.md の「2つ目の部品が使うようになったら `src/internal/` へ移す」規則に沿っています
- `design/backlog.md` から消す案: 「本文（Prose・CodeBlock など）」の「Prose は…見た目は各部品に持たせ、素の要素に CSS を当てる形にはしません」という行を、この決定に合わせて書き換えるか消す必要があります
- `design/backlog.md` に足す案: Prose が想定する HTML の形（GFM の脚注や、チェックリストの `<li>` の属性など）と、実際に流し込む変換ツール（remark-gfm など）が出す形が一致するかは、ブログ側で実際に組んでから確かめる必要があります

## 原則への反映

反映なし。Prose の受け取り方や対応表の有無は、原則ではなく部品の作りとして記録します。
