# 0047. 原則の読まれ方の検証と、一覧の項目・チェックボックスの決まり

- ステータス: Accepted
- 日付: 2026-09-13
- ラウンド: ループ外（原則の検証）

## 背景

principles.md を「考えと現れ方」だけの形に書き直したあと、原則が意図どおりに読まれるかを確かめました。原則だけ（2 回目は tokens.css も）を読ませた Haiku に、Button・Checkbox・Menu を設計させ、部品ごとに 2 体の答えの違いと、既存の決定（ADR）とのずれを見ました。1 回目は言葉で、2 回目は HTML で描かせて撮影しました。

Button は既存の部品で、ADR の決定と照合できます。Checkbox と Menu は未作成で、原則に書いていない判断が浮かび上がります。

## 候補

比較の候補はありません。検証の結果から、原則の文が足りない箇所と、原則に無い判断を洗い出しました。

| 読み違いが重なった箇所               | 2 体の答え                         | 決定・期待                          |
| ------------------------------------ | ---------------------------------- | ----------------------------------- |
| 押下の影（原則 3）                   | 「影がさらに減る」「薄くする」     | 影は hover のまま。沈むだけ（0033） |
| 一覧の項目のキーボード選択           | 4 体すべてが青い線                 | hover と同じ塗り（0036、0044）      |
| 一覧の続きの印                       | 「さらに表示」の行、下端のフェード | 上下の端の内側の影（0037）          |
| 浮かぶ面の角                         | カードの角／部品の角               | 部品の角（0036）                    |
| 矢印の位置（ボタンの見た目のリンク） | ラベルの前に置いた体があった       | ラベルの後ろ（0046）                |
| チェックボックスの仲間               | 影あり／なし、枠線のみ／塗り       | 原則に無い                          |
| チェックボックスの横の文字           | 無効で薄くする／しない             | 原則に無い                          |

## 決定

原則の文を書き換えるものと、新しく決めたものがあります。

1. **一覧の中でキーボードで選んでいる項目は、線ではなく hover と同じ塗りで示します。** 線を引くのは、一覧の外にある部品です
2. **一覧が途中で切れるときは、上下の端の内側の影で続きを見せます。** 文字やぼかしでは知らせません
3. **浮かぶ面（選択肢、メニュー）は部品の角です。** シートはカードの角です
4. **押しても影は hover から変えず、色も薄くしません。** 変わるのは、わずかに沈むことだけです
5. **ボタンの見た目のリンクの矢印は、ラベルの後ろに置きます**
6. **チェックボックスとラジオは、入力欄の仲間です。** ふだんはグレーの塗りで枠線も影もなく、選ぶと色の塗りに白い印になります。チェックボックスは角丸の四角、ラジオは完全な丸で見分けます
7. **チェックボックスの横の文字は本体の一部です。** 押しても反応するので、無効では本体と一緒に薄くなります
8. **チェックボックスのエラーは、箱の塗りを淡い赤にし、エラーの文はグループの見出しに、入力欄と同じ形で付けます**
9. **一覧の項目は、押しても沈みません。** 押した瞬間に一覧が閉じるためです
10. **危険な項目の hover は、赤を淡く敷きます。** 赤い枠線のボタンと同じです
11. **部品の色によらず青が既定なのは、フォーカスの線だけです。** 選んでいることを示す印（一覧で選んだ項目、チェック、トグルの ON）は部品の色に従い、指定しないときはグレーです。Select の選んだ項目の青（[ADR-0036](./0036-select-popup.md)）は、この決まりに合わせて見直します

トークンで満たされていること（グレーの枠線のボタンの文字の濃さ、無効の薄さの値）は、原則に書き足しません。原則はトークンの根拠を書く場所で、トークンの値を繰り返す場所ではないためです。

## 理由

ユーザーのメモです。

> 配色（無効色など）のブレはデザイントークンによるものもありそうですね。デザイントークンも参考として貼っていいのかも。
> 原則→デザイントークンの順に反映しているので、デザイントークンで満たされていることは改めて説明したくないですね。逆に、デザイントークンの根拠は説明したいです。

> チェックボックスとラジオは仲間ですが、明確に区別できるように完全な丸と角丸四角には分けたいですね。
> チェックボックスの文字はラベルですが、標準ではラベルをクリックしても反応すると思うので、実質本体と同じで、色は薄くなるのが正しいかなと思いました。

> エラーについては、箱の塗り＋見出しに対するバリデーションエラー表示（従来のものに揃える）でいいかなと思いました。
> 選択肢は押した瞬間に消えるので、沈まなくていいと思います。

> 危険な項目の hover は淡い赤ですね。danger な outline ボタンと似たイメージです。

2 回目の画像で、色を指定しないチェックボックスの選んだ状態が青とグレーに分かれ、Select の選んだ項目が部品の色によらず青であることを確かめたあとのメモです。

> 配色でデフォルトグレーのものとprimaryのものが混ざっているかもですね、ちょっと見てもらえますか？

> フォーカスカラーは青デフォルト、それ以外はグレーデフォルト、でよさそうです。

以下は、検証から読み取れることです。

- 言葉で答えさせた 1 回目は、チェックボックスに 2 体とも影を付けました。tokens.css も渡した 2 回目は、2 体とも付けませんでした。トークンがあると、原則の言葉だけより決定に近づきます
- Menu の項目の hover は、1 回目は 2 体とも「文字の色を淡く敷く」でしたが、描かせるとグレーの面でした。言葉より絵のほうが決定に近い判断をしています
- それでも 4 体すべてが一覧のキーボード選択に線を引きました。原則 2 の「線」の適用範囲が書かれていなかったためです

## 却下した案と理由

- **グレーの枠線のボタンの文字の濃さを原則に足す**: トークンで満たされているので足しません
- **チェックボックスを白い面に枠線で描く（2 体の答え）**: 入力欄の仲間にし、グレーの塗りにします

## 影響

- `principles.md`: 原則 1（続きの印、押して反応する文字）、原則 2（一覧のキーボード選択、フォーカスの線の既定の色）、原則 6（選んでいることを示す印の色）、原則 3（押下の影と色、一覧の項目の hover と沈まないこと、危険な項目）、原則 5（浮かぶ面の角、チェックボックスとラジオの形）、原則 7（矢印の位置）、原則 8（チェックボックスとラジオ）を書き換えました
- `backlog.md`: Checkbox・Radio を、この ADR の決まりで作る部品として足しました。Select の選んだ項目の色（部品の色に従い、既定はグレー）を見直す軸を足しました。hover のグレーとの見分け方を比べてから、ADR-0036 の該当箇所を置き換えます
- 検証の手順（原則だけを読ませた Haiku に描かせ、同じ Chrome で撮る）は、原則を大きく書き換えたときに繰り返せます。道具はまだリポジトリに入れていません
- **分かっていること**: 検証は Haiku 2 体ずつで、同じ読み違いでも偶然の可能性があります。Checkbox と Menu は未作成なので、決まりは部品を作るときに比べ直すことがあります
