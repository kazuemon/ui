# 検証（1 体分）

あなたは、このライブラリの原則だけを頼りに部品を設計する検証役です。目的は良い設計を出すことではなく、**原則を読んだ人がどう判断するかを記録する**ことです。あとで別の 1 体の答えと比べ、割れたところを「原則の空白」として拾います。

引数: `ISSUE: <番号> SEAT: <A か B>`

## 読むもの（これ以外は読まない）

1. Issue の本文（`gh issue view <番号>`）。部品の名前、どこで要るか、参考
2. `design/principles.md`
3. `design/tokens.css`

`src/`、ADR、backlog、既存の部品、点検表は読みません。既存の部品を見ると、原則ではなく実装をなぞってしまうためです。Issue のコメントも読みません（先に書かれた別の席の答えに引きずられないため）。

## 書くこと

次の見出しをこの順で使い、Markdown で書きます。見出しをそろえるのは、2 体の答えを機械的に並べるためです。各項目は 1〜3 文で、迷ったら「原則 N をこう読んだ」と読み方を添えます。

```
## 検証 <SEAT>

### 構造
要素の並び（ラベル / 本体 / キャプションの 3 層に当てはめる）。Base UI のどの部品を土台にするか

### 見た目
- 通常:
- hover:
- 押下:
- フォーカス（キーボード）:
- 無効:
- エラー（あれば）:
- 送信中・読み込み中（あれば）:

### 色
利用者が選ぶ色か、状態の色か。指定しないときの見た目

### 角と影
どの角か。影があるか、その根拠

### 密度
指用で何が変わるか。構造が変わるか

### 読み上げ・キーボード
名前・説明の付け方。キーボードの操作

### props
名前と値の候補。既定値

### 原則で決められなかったこと
原則を読んでも決められず、自分で決めた点。1 行ずつ「何を・どう決めたか・迷った読み方」
```

## 出し方

メモを Write で `/tmp/probe-<SEAT>.md` に書き、Issue にコメントとして投稿します。

```sh
gh issue comment <番号> --body-file /tmp/probe-<SEAT>.md
```

ファイルに書けないときは、`--body` に本文をそのまま渡します。コメントは 1 回だけです。投稿したら終わります。まとめの文や挨拶は書きません。最後の返事に本文を書いても Issue には届きません。
